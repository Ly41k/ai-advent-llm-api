# Бублик — сохранность истории и перенос, этап 1

База работы: опубликованный `main` commit
`115247d6a2fb73788f22271991bb3445000ca12e`. Это дополнение после задания дня 30,
а не изменение результатов его исторических испытаний. Первый этап не менял
runtime 0.8.0 / API v1 / schema 2. Текущая версия 0.10.0 использует schema 3;
archive v1 проверяет точные схемы 2 и 3. [Обновление](LANGUAGES.ru.md).

## Что уже сохранялось и что добавлено

Сервис уже сохраняет полную историю в SQLite WAL/FULL. Сокращение окна контекста
не удаляет старые сообщения. Однако сохранение истории не означает, что модель
умеет находить и использовать все её события: сейчас она получает недавние пары.

Первый дополнительный этап — проверяемая переносимость исходных данных:

- `scripts/memory_archive.py create`: согласованный снимок через существующий
  SQLite backup API, включая committed WAL; отдельный новый приватный каталог.
- `verify`: SHA-256 файла, целостность SQLite, foreign keys, точная поддерживаемая
  схема/миграции, количества и потоковые хеши содержимого всех таблиц.
- `restore`: только новая база в приватном каталоге. Исходная рабочая база и архив
  сохраняются. Повторная команда не перезаписывает уже существующий файл.
- Владельцы и пароли, IDs диалогов/сообщений/генераций, полный текст, partial/failed
  ответы, порядок, timestamps, исходные profile/context snapshots, events,
  idempotency receipts и stream versions сохраняются без преобразования.
- На восстановленной установке удаляются browser sessions и отзываются API tokens.
  Это явное исключение из побайтовой эквивалентности всех таблиц. Нужен новый вход
  тем же username и новые токены для внешних приложений. Исходная авторизация
  действующего сервиса не меняется.
- Формат не переносит Ollama weights, venv, launchd, Caddy, сертификаты и Tailscale.
  Они устанавливаются отдельно; пути, hostname и origins на новом хосте задаются заново.

Архив содержит ровно `snapshot.sqlite3` и `manifest.json`. Каталог имеет права
0700, файлы — 0600. Manifest содержит хеши/счётчики, а не личный текст или секреты.
Сам SQLite snapshot содержит всю переписку и хеши паролей — он **не зашифрован**.
Хеши выявляют повреждение; не являются подписью и не защищают от подмены файла
вместе с manifest. Используйте свои доверенные архивы. Не публикуйте их в Git,
видеозаписях или открытом облачном каталоге; шифрование переносимого архива пока
не реализовано. Для копий на носителе сохраняйте/восстановите приватные POSIX права.

## Установка дополнения

Устанавливайте файлы с объединением содержимого каталогов, а не заменой целого
каталога `day-30-private-ai-service`, `scripts` или `tests` в Finder. Частичная
поставка зависит от прежних `scripts/check_storage.py`, `scripts/verify_report.py`,
`tests/test_storage.py` и кода сервиса. Если они отсутствуют, полная поставка
`bublik-memory-stage1-complete.zip` позволяет восстановить недостающие файлы.
При восстановлении используйте `cp -R -n` из извлечённого каталога в корень repo:
существующие файлы и исторические отчёты не перезаписываются. Добавляются
два scripts, один test module и эта инструкция. Код `bublik_service`, зависимости,
миграции и профиль модели остаются прежними. API перезапускать из-за установки
этих файлов не требуется. Остановка ниже нужна для принятого сценария переноса.

Работайте из `day-30-private-ai-service`, с корневым virtualenv:

```bash
source ../.venv/bin/activate
python --version
```

На целевом Mac требуется Python 3.13 и зависимости текущего сервиса.

## 1. Сначала тесты без личной базы

```bash
BUBLIK_MEMORY_CHECK="$(mktemp -d "$HOME/bublik-memory-check.XXXXXX")"
python -W error::ResourceWarning scripts/check_memory_archive.py \
  --output "$BUBLIK_MEMORY_CHECK/portability.json"
python scripts/verify_report.py "$BUBLIK_MEMORY_CHECK/portability.json"
```

Это реальные SQLite/files/processes с синтетической перепиской: 18 новых тестов
и 51 прежний storage regression. Не доказательство модели, сети или другого Mac.
В среде разработки итоговый прогон **69/69** прошёл на Linux x86_64,
Python **3.12.14**, SQLite **3.53.1**, за **1.345 s**, без errors/failures/skips.
Исходный отчёт: `reports/verified/memory-portability-linux-final-20261011.json`.
Предварительный отчёт сохранён отдельно; он относится к предыдущей редакции теста.
Это проверка stdlib-инструмента хранения, не полноценного API на Python 3.12.
Для полной текущей HTTP/SQLite regression-проверки на Python 3.13:

```bash
python -W error::ResourceWarning scripts/check_storage.py \
  --output "$BUBLIK_MEMORY_CHECK/full-offline.json"
python scripts/verify_report.py "$BUBLIK_MEMORY_CHECK/full-offline.json"
```

Все пути отчётов новые. Исторический `stage8-prompt-v2-offline.json` сохраняет
результат 143/143 на предыдущих 67 source files; после добавления scripts/tests
его full-source hash guard закономерно не совпадёт с новым checkout. Runtime
из 27 файлов остаётся прежним. Не переписывайте старый JSON, чтобы вернуть PASS.

## 2. Согласованный снимок рабочей истории на Mac

Дождитесь «Ответ сохранён» для всех активных ответов и прекратите отправки со всех
устройств. Остановите только API и дождитесь отсутствия listener 8000:

```bash
launchctl bootout "gui/$(id -u)/local.bublik.private-ai.api"
/usr/sbin/lsof -nP -a -iTCP:8000 -sTCP:LISTEN
```

Если сервис уже остановлен, повторный bootout не нужен. Не запускайте второй
API или terminal chat. В новом терминале переменные нужно задавать заново:

```bash
BUBLIK_MEMORY_DB="/Users/litdi/bublik-day30-stage4.V1EM3F/chats.sqlite3"
BUBLIK_MEMORY_ARCHIVE="$HOME/bublik-memory-archives/$(date +%Y%m%d-%H%M%S)"
python -m bublik_service --db "$BUBLIK_MEMORY_DB" storage-status
python scripts/memory_archive.py create \
  --db "$BUBLIK_MEMORY_DB" --output "$BUBLIK_MEMORY_ARCHIVE"
python scripts/memory_archive.py verify --archive "$BUBLIK_MEMORY_ARCHIVE"
```

Ожидается schema 3 в текущем сервисе (2 у прежнего snapshot), integrity `ok`, queued/running 0, recovery_required false,
`created`/`verified` и **restorable_now=true**. Не создавайте каталог архива заранее.
Сохраните значение `BUBLIK_MEMORY_ARCHIVE`; его нельзя угадывать в другом окне.

Backup может быть снят и во время работы модели. Такой архив сохраняет состояние,
но при queued/running/recovery gate показывает `restorable_now=false`. На этом
первом этапе его восстановление запрещено: нет автоматического replay или
догадок об inference на другом хосте. Не удаляйте вопросы/partial и не обнуляйте
gate в SQL. Завершите очередь или выполните существующий проверенный recovery
на исходном сервере, затем создайте новый idle snapshot. Аварийный перенос
незавершённых заданий требует отдельного этапа восстановления.

## 3. Репетиция восстановления на том же Mac

Создаётся отдельная база — это не переключение работающего чата:

```bash
BUBLIK_MEMORY_RESTORE="$(mktemp -d "$HOME/bublik-memory-restore.XXXXXX")"
python scripts/memory_archive.py restore \
  --archive "$BUBLIK_MEMORY_ARCHIVE" \
  --db "$BUBLIK_MEMORY_RESTORE/chats.sqlite3"
python -m bublik_service --db "$BUBLIK_MEMORY_RESTORE/chats.sqlite3" storage-status
```

Ожидается `restored`, `history_tables_unchanged=true`, sessions_cleared=true,
api_tokens_revoked=true, inference_replayed=false. Каждый сохранённый ряд всех
неавторизационных таблиц сравнивается до публикации файла. SQLite integrity
дополнительно проверяется. Старые личные API tokens из исходной установки не
проверяйте на восстановленной копии: они намеренно отозваны.

Исходный API после репетиции поднимается **на прежней базе из существующего plist**:

```bash
launchctl bootstrap "gui/$(id -u)" \
  "$HOME/Library/LaunchAgents/local.bublik.private-ai.api.plist"
```

Проверьте прежний чат на Mac и телефоне. Не меняйте рабочий plist/DB ради этой
проверки и не обслуживайте обе копии как один синхронизируемый сервер.

## 4. Перенос на другое железо

1. Сделайте проверенный idle archive и перенесите **весь каталог**, оба файла.
   При копировании восстановите права: каталог 0700, оба файла 0600; владелец —
   пользователь нового хоста. Снимок рабочей SQLite вручную не копируйте.
2. На новом macOS/POSIX-хосте установите текущую совместимую версию сервиса,
   Python 3.13, локальную Ollama и проверенный профиль Qwen. Для переноса истории
   сама модель не нужна; для продолжения inference она требуется.
3. Выполните `verify`, затем `restore --db <NEW_PRIVATE_DIR>/chats.sqlite3`.
   Путь должен быть новым, без существующих SQLite/WAL/SHM/journal файлов.
4. Выполните `storage-status` и `doctor` на восстановленной базе. Настройте новый
   HTTPS hostname, origins, Tailscale Serve и launchd, используя **эту** базу.
5. Войдите прежним username/паролем, проверьте старые диалоги и partial/failed
   ответы, создайте один новый ход. Переподключите телефоны к новому URL.
6. Прежний сервер оставьте остановленным после итогового снимка. Изменения,
   сделанные на нём после снимка, не окажутся в новой копии автоматически.
   Имя/URL и архив не обеспечивают синхронизацию двух серверов.
7. Не удаляйте старую базу/архив до приёмки новой установки. Сделайте новую
   проверяемую резервную копию после успешного продолжения диалога.

Физический перенос на другое оборудование пока не испытан здесь. Пример нового
OS host не считается проверенным по тесту двух каталогов на одном компьютере.
Текущий инструмент принимает точные schema 2/3 с проверенными migrations.
Create не мигрирует исходную базу. Restore сохраняет схему архива; открытие
восстановленной schema 2 новой версией отдельно мигрирует копию до 3. Языковые
настройки schema 3 включаются в архив; старый инструмент не принимает новую схему.

## Границы первого этапа и следующие этапы

| Этап | Результат | Статус |
|---|---|---|
| 1 | Сохранность исходной истории, verified backup/restore и IDs | Реализовано; рабочая база проверена оператором на том же Mac; новый хост отдельно |
| 2 | Явная долговременная память: факты/предпочтения с источником сообщения, версиями и журналом исправлений | Требует отдельной реализации API/UI и миграции |
| 3 | Поиск старых событий и подбор памяти в inference context с лимитами/прозрачностью | FTS5 retrieval обеих сторон переписки в0.9.1; семантический поиск и live-качество отдельно |
| 4 | Зашифрованные off-host копии, расписание, retention, аварийный restore и регулярная репетиция переноса | Не реализовано |

Исходные сообщения служат независимым первоисточником. Будущие summaries/facts
не должны заменять оригинал; автоизвлечение моделью не должно молча перезаписывать
подтверждённую память. Это не утверждение, что текущая Qwen помнит всю жизнь чата.
Автоматическое забывание или удаление старых данных не добавлено.

## Расширение RAG в0.9.1

В расширении0.9.1 основная схема оставалась2; текущая0.10.0 использует3. Исходные архивы0.8.0 совместимы. RAG sources и точный
inference context сохраняются в `generations.context_json` и входят в archive.
Отдельный приватный `memory-index/` cache не входит в архив и пересоздаётся
из всех accepted user messages и непустых terminal assistant messages. История/IDs не переписываются.
См. [RAG_MEMORY.ru.md](RAG_MEMORY.ru.md). Старые JSON остаются свидетельствами
прежних исходников; их source guard не должен совпадать с runtime0.9.1.
