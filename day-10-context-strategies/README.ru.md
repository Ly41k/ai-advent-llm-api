# День 10 — разные стратегии управления контекстом без summary

В десятом задании Бублик использует одну SQLite-память, но формирует prompt тремя разными способами: Sliding Window, Sticky Facts и Branching. Накопительный summary из Дня 9 не используется.

## Реализованные стратегии

### 1. Sliding Window

В модель отправляются только последние 6 завершённых сообщений. Полный журнал остаётся в SQLite, но ранние сообщения не участвуют в генерации.

```text
system prompt + последние 6 сообщений + текущий запрос
```

Преимущества: минимальная стоимость, простое и предсказуемое поведение. Недостаток: ранние требования исчезают из контекста.

### 2. Sticky Facts / Key-Value Memory

После каждого сообщения пользователя отдельный запрос к GPT-OSS 20B обновляет полный JSON-объект с устойчивыми фактами: целью, ограничениями, предпочтениями, решениями и договорённостями. Затем основной модели отправляются facts и последние 6 сообщений.

```text
system prompt + key-value facts + последние 6 сообщений + текущий запрос
```

Facts сохраняются в таблице `facts`. Токены и стоимость их извлечения сохраняются отдельно в `fact_update_usage` и включаются в `/stats`.

### 3. Branching

Checkpoint фиксирует место в активной ветке. От него можно создать несколько веток. Каждая наследует историю только до checkpoint, а её последующие сообщения не видны соседним веткам.

```text
main ── checkpoint ── research
                   └─ economy
```

В модель отправляется полная унаследованная история активной ветки. Это удобно для исследования альтернатив, но длинная ветка расходует больше токенов и в итоге может заполнить контекстное окно.

## Запуск

```bash
pip install -r requirements.txt
python day-10-context-strategies/main.py
```

При создании диалога программа предлагает выбрать стратегию. Позже её можно изменить:

```text
/strategy sliding
/strategy facts
/strategy branching
```

Другие команды:

- `/history` — журнал активной ветки с учётом наследования;
- `/context` — точный контекст, который выбранная стратегия отправит модели;
- `/facts` — текущая key-value память;
- `/checkpoint NAME` — сохранить checkpoint в текущем месте;
- `/branches` — показать ветки и checkpoints;
- `/branch create NAME CHECKPOINT` — создать ветку от checkpoint;
- `/branch switch NAME` — переключить активную ветку;
- `/stats` — токены и стоимость основных запросов и обновления facts;
- `/dialogs` — выбрать другой диалог;
- `/exit` — завершить программу.

Пример двух веток из одной точки:

```text
/strategy branching
/checkpoint base
/branch create research base
/branch create economy base
/branch switch research
```

## Одинаковый тестовый сценарий

`experiment.py` собирает ТЗ корабля из 11 последовательных требований и затем просит подготовить итоговое ТЗ. Для Sliding Window и Sticky Facts используется один и тот же список сообщений. Для Branching первые 7 требований становятся общим checkpoint, после чего создаются независимые ветки `research` и `economy`.

```bash
python day-10-context-strategies/experiment.py
```

Эксперимент делает реальные запросы к Groq и выводит:

- итоговый ответ каждой стратегии;
- суммарное число токенов;
- полную стоимость, включая отдельные вызовы обновления facts;
- два независимых результата Branching для проверки отсутствия смешения решений.

Из-за минутных ограничений Groq между сериями может потребоваться пауза. Результаты генерации могут отличаться между запусками.

## Сравнение

| Критерий | Sliding Window | Sticky Facts | Branching |
|---|---|---|---|
| Качество длинного диалога | Снижается после выпадения ранних сообщений | Обычно сохраняет ключевые требования | Высокое внутри выбранной ветки |
| Стабильность важных деталей | Низкая для ранних фактов | Высокая для корректно извлечённых facts | Высокая, пока ветка помещается в окно |
| Расход prompt tokens | Самый низкий | Низкий/средний | Растёт вместе с веткой |
| Дополнительные API-вызовы | Нет | Один на каждое сообщение пользователя | Нет |
| Удобство | Не требует действий | Не требует ручного управления памятью | Требует checkpoints и переключения веток |
| Лучший сценарий | Короткий локальный диалог | Долгое последовательное ТЗ | Параллельное исследование альтернатив |

Качество оценивается по четырём проверкам: сохранилась ли ранняя цель, не потерялись ли числа, не появились ли выдуманные требования и не смешались ли решения соседних веток.

## Локальные тесты

```bash
python -m unittest discover -s day-10-context-strategies -p "test_*.py" -v
```

Тесты не вызывают Groq и проверяют размер Sliding Window, добавление facts перед недавней историей и независимость двух веток от одного checkpoint.

## Ограничения

- извлечение facts зависит от качества модели;
- facts общие для диалога, поэтому сравнивать ветвящиеся альтернативы следует в стратегии Branching;
- при переключении существующего длинного диалога на Facts ранние сообщения не обрабатываются задним числом;
- Branching не сокращает историю и может переполнить контекст модели;
- оценка качества остаётся ручной, без отдельной Judge-модели.

## Итог

Бублик умеет переключать три стратегии без удаления полного журнала, сохраняет key-value facts, создаёт независимые ветки от одного checkpoint и показывает реальную цену каждого подхода.
