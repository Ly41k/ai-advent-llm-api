Это подтверждает воспроизводимость, а не правильность. `local_rag_verified=true` подтверждает локальную генерацию; `all_checks_passed=false` остаётся корректным.

V9 заменяет накопленную длинную англоязычную инструкцию более короткой русской. Ответ по-прежнему нужен на языке вопроса. Для сохранения/перезапуска модель должна явно назвать хранилище и данные, объяснить загрузку истории и ограничение контекста по идентификатору. Тестовые имена тем нельзя выдавать за обычный startup; для вопроса о механизме нужны описания работы программы. Для вопросов о генерации сохраняются требования объяснить проверки до запроса и после ответа; для команд — точные команды из источника. Название SQLite или эталонный ответ в prompt не подставляются.

Каталог sections_v8, JSON-контекст objects_v8 и контракт evidence_claims_v8 остаются прежними. Меняется prompt_revision=concise_mechanism_ru_v9 и schema_version=9. Приложение собирает только утверждения модели; скрытых исправляющих генераций нет. Retrieval, индекс Недели 6, другие дни не меняются; переиндексация не нужна. Изменение prompt не гарантирует правильный live-ответ.

Следующий запуск — **одна диагностическая проба одного оставшегося вопроса**, без облака и повторения прошедших вопросов:

```bash
python day-28-local-rag/main.py evaluate --retry-from day-28-local-rag/reports/check/local-retry-v8.json --repeats 1 --output day-28-local-rag/reports/check/local-probe-v9.json
python day-28-local-rag/verify_report.py day-28-local-rag/reports/check/local-probe-v9.json
```

Одна проба проверяет качество и корректность выполнения, но не стабильность. Три повторения для итоговой оценки стабильности выполняются после успешного ответа. Для этого нужно планировать снова от сохранённого неуспешного `local-retry-v8.json`, с repeats=3 и новым output: retry от прошедшего одноразового probe заморозит эту пару и не создаст новые испытания. Старые успешные пары остаются историческими; это не свежая валидация всего набора на V9. Облачные ошибки пока открыты.
