# V7 — утверждение и доказательство в одном объекте

Исходный local-retry-v6, run ID `7c798453-9c22-4adc-a97b-863fd8d70231`: три валидных локальных ответа, качество 0/3. SQLite есть в ответе, но отсутствует в выбранных цитатах. UUID/conversation_id подтверждены. Ответ описывает выбор диалога при старте, но не уточняет загрузку сохранённой истории. Строгий verifier отклоняет отчёт; отдельная проверка внутренней согласованности проходит. Прямые доказательства хранилища и восстановления доступны в извлечённых источниках. Это проблема согласования ответа с выбранными доказательствами.

Медиана generation wall time на одном вопросе — 14,26 с, первая проба 59,05 с, последующие около 14,26 с. Retrieval: медиана 0,075 с. Все три ответа одинаковы; стабильность не означает достаточную доказательность. `local_rag_verified=true` подтверждает локальную генерацию, `all_checks_passed=false` корректно отражает провал оценки качества.

В V7 вместо отдельного `answer` и списка IDs модель возвращает:

```json
{
  "claims": {
    "c1": {"quote_id": "e1-q1", "statement": "Сформулированное моделью утверждение по этому фрагменту."},
    "c2": null,
    "c3": null,
    "c4": null
  },
  "abstained": false
}
```

Приложение соединяет только `statement` непустых слотов, в порядке c1–c4, через перевод строки. Оно не дописывает факты или готовый правильный ответ. Для каждого утверждения вставляется точная цитата по его ID, в том же порядке. Это делает привязки явно проверяемыми, но не доказывает смысловую поддержку: модель всё ещё может связать утверждение с неподходящим источником. Прежняя строгая оценка SQLite/идентификатора и ручная смысловая проверка остаются необходимыми.

Prompt требует писать каждое утверждение по своему фрагменту. Для вопросов о перезапуске: c1 объясняет постоянное хранилище, c2 — восстановление истории, c3 — изоляцию по идентификатору; названия хранилища и IDs не берутся из эталона, их должна выбрать модель из источников. Нельзя тратить слоты на общий итог или дубли одного факта в разных переводах.

Форма проверяется строго: четыре обязательных nullable слота; каждый непустой объект содержит только quote_id/statement; неизвестные и повторные IDs, пустые/нетекстовые утверждения, отдельный answer и ложный отказ отклоняются. У отказа все четыре слота null; приложение подставляет прежний канонический текст. При пустом retrieval модель по-прежнему не вызывается.

Один generation-вызов на пробу, без скрытого ремонта. Ollama получает JSON Schema с enum ID; Groq GPT-OSS — ту же схему в strict mode, прочие облачные модели — JSON object mode. Live совместимость с Groq и квоты пока не проверены. Ни облако, ни пройденные вопросы в следующем local-запуске не вызываются.

Новый report: schema_version=7, prompt_revision/output_contract=evidence_claims_v7; каталог passages_v4 остаётся прежним. Verifier пересобирает утверждения и цитаты из raw JSON и проверяет их против сохранённого отчёта. Контракты V2–V6 сохранены для исторических файлов без исправления их результатов. Индекс Недели 6, retrieval и другие дни не меняются, переиндексация не нужна.
