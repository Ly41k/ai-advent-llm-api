## Полностью локальный запуск

Параметры идут после команды:

```bash
python day-28-local-rag/main.py doctor
python day-28-local-rag/main.py ask "Какой процесс выполняет фоновые задания на Day 18?" --synthesis
python day-28-local-rag/main.py evaluate --repeats 3 \
  --output day-28-local-rag/reports/check/local.json
```

`doctor` проверяет индекс и установленные локальные модели, без генерации. `ask` и `evaluate` выполняют реальные embedding и generation. В V8 модель возвращает `claims` (четыре nullable слота c1–c4) и `abstained`. Каждый непустой слот содержит `quote_id` и `statement`: ID доказательства и сформулированное моделью утверждение. Приложение соединяет утверждения в `answer` и подставляет точные исходные цитаты и метаданные источников. CLI выводит ответ и источники; исходный JSON модели сохраняется в `generation.answer`, включая невалидные ответы для диагностики. Структурная привязка не доказывает смысловую поддержку утверждений.

При пустом, отфильтрованном или полностью исключённом бюджетом контексте приложение возвращает отказ и не вызывает генерацию. Отказ модели с непустым контекстом требует канонического текста и пустого списка цитат. Если все запросы закончились только отказами приложения, `local_rag_verified=false`: это не подтверждает работу LLM.

`local_rag_verified` требует хотя бы одного валидного ответа локальной модели с RAG, успешного local preflight и подтверждения загрузки модели через `/api/ps`. Для принятия всего прогона также не должно быть ошибок, обрезанных/невалидных ответов и проваленных эвристических проверок. Семантическая проверка человеком всё равно нужна.

## Качество, скорость, стабильность

**Качество:** JSON-контракт, точные цитаты, ожидаемые термины в ответе и ожидаемые процитированные источники. Отрицательные вопросы проверяют отказ. Эвристики могут ошибаться при перефразировании или вводящей в заблуждение формулировке. Точная цитата не доказывает, что поддерживает весь ответ. Проверяй ответы рядом с цитатами и ожиданиями.

**Скорость:** время retrieval, generation wall time, их сумма; median и интерполированный p95. Отказы приложения и неуспешные генерации исключены из итоговых скоростей; ошибки считаются отдельно. Первый повтор может включать загрузку модели. `/api/ps` после генерации не входит в её время. Cloud latency включает сеть; токенизаторы провайдеров разные. Сохраняются исходные Ollama load duration и throughput. Маленькая выборка не даёт общего рейтинга моделей.

**Стабильность:** минимум два валидных повтора и отсутствие проваленных повторов для данного вопроса. Сравниваются точные текст/цитаты, а не семантическая эквивалентность. Каждый повтор заново выполняет retrieval; SHA prompt позволяет заметить изменения контекста. Ошибки и неполные ответы отражены отдельно.

## V2 — структурированный JSON и цитаты приложения

В первом живом ответе появилась лишняя кавычка после JSON, а обе цитаты потеряли обратные кавычки вокруг `worker.py`. Исходный отчёт остаётся невалидным. V2 не исправляет этот ответ задним числом и не ослабляет проверку.

Ollama получает `format` с JSON Schema и enum допустимых IDs цитат. Groq получает `response_format={"type":"json_object"}`; приложение дополнительно проверяет форму и IDs. Контроли вывода провайдеров отличаются и записаны в отчёт. При этом prompt/контекст у пары одинаковы; генерация одна, скрытых запросов исправления нет.

Приложение извлекает точные строки/предложения из найденных чанков с сохранением отступов кода и пунктуации. Контекст маркирует их IDs; модель возвращает `answer`, `abstained`, `quote_ids`. Неизвестные/повторные IDs или пустой список для фактического ответа отклоняются. Цитаты подставляются из источников по IDs, без перепечатывания моделью. Правильность выбора доказательств всё ещё требует смысловой проверки.

Отчёты V2: `schema_version=2`, `output_contract=quote_ids_v2`, каталог цитат. Verifier сверяет каталог с исходными фрагментами и проверяет raw selection. Старый exact-quote контракт остаётся поддержан при проверке прежних отчётов; невалидные ответы остаются отклонёнными. Корпус Недели 6 этим обновлением не изменён, валидный индекс пересобирать не нужно.

Для изоляции диалогов требуется SQLite и один из терминов идентичности (`conversation_id`, UUID, identifier, идентификатор). Это эвристики, а не семантический аудитор.

Новый prompt требует полного механизма и доказательств для всех частей вопроса; рекомендует 1–4 цитаты и явно запрещает больше 12, дубли и выбор всего каталога. GPT-OSS в Groq получает strict JSON Schema с enum IDs и `maxItems=12`; неизвестные/повторные IDs и фактические ответы без доказательств всё равно проверяются приложением. Ошибки 400/401/403, таймауты и невалидные ответы не повторяются. `transport_attempts` сохраняет ошибки, ожидания и успешную попытку. Generation wall time включает все попытки и ожидание; лимит аккаунта может остаться непреодолимым. Если HTTP 429 сохраняется после всех попыток, оставшиеся cloud-вызовы в этом прогоне пропускаются с явной ошибкой; local продолжает работу. Это предотвращает повторные долгие ожидания на каждом вопросе.

Отчёт `schema_version=3`, `scope=selective_retry` содержит только новые наблюдения. `all_checks_passed` и метрики относятся **только к этому подмножеству**; успех не означает повторную валидацию всего набора на V3. Старые результаты не смешиваются с новыми в общий benchmark. Парные промпты совпадают только там, где обе модели заново запланированы; непарный retry не сравнивается с историческим ответом как новая одинаковая пара. Cloud-only retry может пройти проверку при `local_rag_verified=false`: локальная генерация в нём не планировалась и подтверждается отдельным baseline.

## V4 — целые доказательства и раздельная проверка провайдеров

Живой retry-v3: local 9/9 валидных результатов, 3/9 эвристических pass. base-01 теперь объясняет SQLite/UUID/восстановление и пройден во всех трёх пробах — его не повторяем. base-03 по-прежнему не объясняет preflight; rewrite-ru-02 объясняет механизм, но выбирает слабые цитаты из EN README.

Cloud: реально выполнено 4 HTTP-попытки: один HTTP 400, затем три HTTP 429 (30/60 секунд ожидания). Остальные 19 запланированных наблюдений отмечены skipped/error без HTTP. Причина 400 в исходной диагностике не раскрыта; считать её доказанным отказом конкретного ключевого слова схемы нельзя. Квота и новый контракт требуют отдельного live-подтверждения.

V4 меняет каталог: вместо отдельных строк — целые исходные абзацы и блоки кода. Отдельные заголовки и Markdown fences не предлагаются как цитаты. Сохранённые фрагменты — точные подстроки чанков. Вопрос/retrieval/chunks не меняются; меняются представление контекста и prompt. При отсутствии подходящих доказательств действует прежний отказ.

Контракт: `quote_ids={"q1":"e1-q2","q2":null,"q3":null,"q4":null}`. Четыре обязательных слота типа string/null ограничивают число цитат самим числом свойств, без массивного maxItems. Оба провайдера получают одну схему и одинаковый prompt при парном запуске; Groq GPT-OSS использует strict mode, прочие cloud модели — JSON object mode. IDs, дубли, форму слотов и точность подставленных цитат проверяет приложение. Это упрощение формата, а не обещание устранения любого HTTP 400.

Prompt явно требует двух частей ответа для проверок вокруг генерации: BEFORE для входного запроса и AFTER для ответа. Для rewrite-ru-02 допустим соответствующий EN README, но процитированные фрагменты также должны содержать SQLite и термин идентичности. Новая проверка лексическая, не доказательство семантической поддержки. Слабый V3 ответ не засчитывается задним числом.

Сначала только локальная проверка — **2 вопроса × 3 = 6 вызовов**, без облачного ключа/API:
