Задание не требует 100% качественных ответов облачной модели. Облачный retry не прошёл строгую проверку, и этот результат сохраняется как часть оценки.

## Локальные выборочные исправления

По текущим рубрикам все 20 локальных вопросов имеют успешные три наблюдения в сохранённой истории: 17 пар удерживаются из compare-v2, base-01 из retry-v3, base-03 из local-retry-v4, rewrite-ru-02 из local-stability-v11. Источники каждой принятой пары перечислены в reports/verified/final-audit-v11.json. Это покрытие историей разных версий, а не полный новый benchmark V11. Пройденные вопросы по решению пользователя повторно не запускались.

Для последнего rewrite-ru-02 V11 отдельно подтверждён:

- качество 3/3, ошибок 0, строгий verifier успешен;
- три финальных ответа и их цитаты полностью совпадают;
- русскоязычный ответ описывает SQLite, conversations/messages, восстановление completed истории и изоляцию через conversation_id;
- ручной просмотр подтверждает эти утверждения выбранной исходной цитатой How It Works;

Первый этап выбирает доказательства; второму передаются только выбранные точные источники и вопрос, без statements первого модельного ответа и без эталонных expected_terms. Второй этап сам пишет финальный ответ. Приложение не добавляет SQLite в текст за модель. Без --synthesis остаётся прежний режим одного вызова.

## Облачный retry V11 и лимиты Groq

21 запланированное наблюдение не означает 21 отправленный запрос. Было 10 HTTP-попыток: 4 успешных и 6 HTTP 429. После устойчивого 429 оставшиеся 16 наблюдений пропущены без HTTP. Валидных ответов 4, качество 3/4, полностью завершённых групп по три повтора нет. Cloud stability для этого subset не оценена. Строгий verifier не проходит; проверка согласованности проходит.

Отдельный дефект качества base-03: ответ описывает postflight и отказ, но пропускает объяснение preflight, хотя доказательства доступны. Задержка запросов этот дефект качества не исправляет. В rewrite-ru-02 механизм SQLite/идентификатора описан; формулировка о completed статусах как причине предотвращения смешивания неточна: изоляцию тем обеспечивает conversation_id, а статусы исключают незавершённые и ошибочные сообщения.

Generation wall median облака 31,11 с включает ожидание повторов. Медиана длительности только успешных HTTP-попыток 1,22 с — отдельная диагностическая метрика, исключающая ожидания и ошибки; её нельзя выдавать за пользовательское время всей пробы. Provider latency_seconds также включает retry waits в текущем HTTP адаптере.

429 подтверждает ограничение API, но сохранённое сообщение не показывает, достигнут ли TPM, TPD или иной лимит. Заголовки retry-after и x-ratelimit-* в текущем отчёте не сохранены, поэтому точное время восстановления неизвестно. HTTP 400 в этом retry отсутствует; текущая структурированная схема дала валидные ответы. Это не доказывает устранение всех возможных 400.

Официальная документация Groq, проверена 2026-10-07: https://console.groq.com/docs/rate-limits . В опубликованной таблице Free Plan для gpt-oss-20b указаны 30 RPM, 1000 RPD, 8000 TPM и 200000 TPD. Точные лимиты своей организации смотрите на странице Limits: https://console.groq.com/settings/limits . Лимиты организации могут отличаться. Примеры входа этого retry: 2788–5791 токен; подряд отправленные запросы способны превысить 8000 TPM — это объяснение возможного механизма, а не доказательство конкретного лимита аккаунта. Дневной лимит не снимается короткой паузой.

## Решение по дальнейшим запускам

Для выполнения Дня 28 новые cloud-запуски и смена API не нужны: сравнение уже существует, качество/скорость/стабильность оценены, ошибки честно зафиксированы. Переход на другого провайдера потребовал бы нового отдельного сравнения и не исправляет локальный RAG. Количество вопросов в задании не задано; текущие 20 и сохранённые повторы достаточны для описания наблюдений, хотя не доказывают общее качество на любых вопросах.

Если позднее нужен дополнительный облачный эксперимент, сначала проверить Limits и время восстановления; затем выбрать заранее небольшой набор общих вопросов для обеих моделей и согласованный режим, выдерживать лимиты по токенам, сохранять retry-after/остатки и отдельно учитывать pacing/retries. Нельзя удалять проваленные вопросы из старого отчёта или представлять новый небольшой subset как полный успешный прогон. Автоматические дополнительные генерации сейчас не запускаются.

## Использование и материалы

Для локального ответа с синтезом:

```bash
python day-28-local-rag/main.py ask "Какой процесс выполняет фоновые задания на Day 18?" --synthesis
```

doctor — только диагностика, его attempts=0 и local_rag_verified=false ожидаемы. Подтверждение генерации даёт ask/evaluate с реальным ответом. Повторять полный evaluate сейчас не требуется. Для проверки успешного сохранённого subset:

```bash
python day-28-local-rag/verify_report.py day-28-local-rag/reports/check/local-stability-v11.json
```

Исходные V2–V11 JSON сохраняются неизменными в reports/check. Аудит: reports/verified/final-audit-v11.json. Код и обновления относятся только к Day 28; корень, другие дни и индекс не меняются, переиндексация не нужна. Отчёты прошлых версий с pending являются историческими записями, актуальное состояние описывает этот итоговый отчёт.
