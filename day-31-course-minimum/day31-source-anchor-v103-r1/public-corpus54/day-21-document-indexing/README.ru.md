# День 21 — Индексация документов и общая база знаний

Создаём локальную базу знаний для следующих дней недели. Корпус: корневые `README*.md`, `README*.md` уроков 1–20 и `.py` верхнего уровня дней 16–20, кроме `test_*`. README уроков начиная с Дня 21 и созданные отчёты исключены. Корневые README содержат обзор всего проекта, поэтому корпус не ограничен исключительно сведениями о днях 1–20. `corpus` выводит точный список файлов, исходный commit SHA с отпечатком содержимого и объём. Эквивалент страниц оценивается как 300 слов текста или 50 строк кода на страницу; это оценка, а не число страниц PDF. Корпус превышает минимум 20–30 страниц.

Обе стратегии используют **одни документы и одну embedding-модель**:

- `fixed`: окно 500 единиц, overlap 75;
- `structural`: секции Markdown по заголовкам, Python по верхнеуровневым функциям и классам; длинные секции дополнительно делятся тем же окном.

Единица разбиения — фрагмент по пробелам (`\S+`), приблизительный токен, **не** точный токенизатор BGE-M3. Поля индекса `limit_tokens` и `overlap_tokens` измеряются в тех же единицах. SQLite хранит `chunk_id`, `source`, `title`, `section`, стратегию, строки, текст и вектор; отдельно модель, размерность, параметры и SHA корпуса. Повторный `build` заменяет чанки, не дублирует их.

## Пошаговая проверка на macOS

Из корня репозитория; готовое `.venv` можно переиспользовать:

```bash
python3.13 -m venv .venv
source .venv/bin/activate
python day-21-document-indexing/test_day21.py -v
python day-21-document-indexing/main.py corpus
```

Основной код использует стандартную библиотеку Python и локальный API Ollama. Установите Ollama и загрузите многоязычную embedding-модель:

```bash
ollama pull bge-m3
ollama serve
```

Если приложение Ollama уже работает, повторный `ollama serve` не нужен. В другом терминале из корня репозитория:

```bash
source .venv/bin/activate
python day-21-document-indexing/main.py build
python day-21-document-indexing/main.py inspect
python day-21-document-indexing/main.py verify
python day-21-document-indexing/main.py search "How does the scheduled worker store GitHub snapshots?"
python day-21-document-indexing/main.py compare
```

На CPU индексация может занять время; прогресс печатается по партиям. При ограниченной памяти попробуйте `build --batch 8`. База по умолчанию — игнорируемый Git файл `day-21-document-indexing/knowledge.db`. Глобальные аргументы `--db PATH`, `--model`, `--url` ставятся **до** команды.

`verify` проверяет наличие обоих индексов, метаданные, размерность и L2-норму сохранённых векторов и совпадение корпуса с текущими файлами. `compare` запускает обе стратегии на одинаковых 15 вопросах из `questions.json`. Печатаются Recall@1, Recall@k, MRR@k, ранг и найденные источники. Проверяется попадание **документа**, а не конкретного предложения или качество ответа. Число чанков и средний размер есть в `inspect`.

## Дополнительные моменты недели

- **Bi-encoder:** `bge-m3` заранее вычисляет векторы чанков; запрос кодируется при поиске. Оба вектора L2-нормализованы, их скалярное произведение равно cosine similarity. В поиске дополнительно показывается `display_01=(cosine+1)/2`; это отображение в `[0,1]`, а не вероятность релевантности.
- **Cross-encoder:** можно переранжировать top-20 кандидатов. Установите `python -m pip install sentence-transformers` и запустите `search` или `compare` с `--rerank-model cross-encoder/mmarco-mMiniLMv2-L12-H384-v1`. При первом запуске модель может скачиваться. Сравнивайте результаты reranking отдельно от сравнения chunking.
- **Агент и локальная Llama:** `ollama pull llama3.2`, затем `python day-21-document-indexing/main.py ask "How does Bublik schedule GitHub collection?"`. `BublikKnowledgeAgent` выполняет поиск в общей базе, передаёт найденные чанки модели и возвращает ответ вместе с источниками. Это отдельный адаптер урока, ещё не слияние со всеми версиями BublikAgent прежних дней.
- **Проверка ответа:** `python day-21-document-indexing/main.py review --number 11` показывает фактический контекст, ответ, наличие эталонных терминов и три пустых поля для ручной оценки: релевантность поиска, подтверждение утверждений контекстом, правильность относительно эталона. Термины и ссылки **не доказывают** правильность.

Для видео достаточно показать по порядку `corpus`, тесты, `build`, `inspect`, RU/EN `search`, `compare`. `ask` и `review` демонстрируют задел на следующие дни.

## Параметры CLI и актуальность индекса

В Дне 21 параметры подключения (`--db`, `--model`, `--url`, `--answer-model`) стоят до команды, а `--strategy`, `--top-k`, `--rerank-model` — после `search`/`ask`. Это отличается от CLI дней 22–23:

```bash
python day-21-document-indexing/main.py --model bge-m3 \
  search "How does the Day 18 worker run?" --strategy fixed --top-k 3
python day-21-document-indexing/main.py --answer-model qwen2.5:7b \
  ask "На 18 дне кто выполняет фоновые задачи?" --strategy fixed
```

Для второй команды отдельно загрузите `qwen2.5:7b`. Смена только answer-модели не меняет embedding-размерность и сама по себе не требует переиндексации; смена embedding-модели требует.

Revision включает **Git HEAD и отпечаток содержимого корпуса**. Корневые README индексируются: после их обновления нужен `build`. Новый коммит также может изменить strict revision, даже если содержимое корпуса не изменилось. Выполняйте `build` и `verify` в окончательной версии checkout. Правка только README урока 21–23 без изменения HEAD не меняет отпечаток корпуса. `knowledge.db` остаётся локальным; число чанков зависит от текущих документов и параметров.

День 22 использует эту базу для сравнения без RAG/с RAG. День 23 — для rewrite, raw cosine-фильтра, candidate/final K и сравнения четырёх режимов. В Дне 23 не включены дополнительный cross-encoder Дня 21 и повтор ответа по одному чанку.

Ограничения: поиск выполняет точный перебор векторов из SQLite, что достаточно для учебного корпуса; FAISS можно добавить позже. После смены модели, корпуса или параметров переиндексируйте обе стратегии. Сгенерированный ответ требует проверки человеком.
