# День 29 — оптимизация локальной LLM под RAG-задачу

В этом задании локальная Qwen RAG-система оптимизирована для короткой справки по репозиторию, отказа при отсутствии доказательств и источниковой процедуры проверки периодического worker Дня 18 на VPS.

Выбрана **Qwen2.5 14B Instruct Q4_K_M** через локальную Ollama на **MacBook Pro M1 с 32 GB RAM**. Embeddings, retrieval и генерация работают локально. Итоговые доказательства V7 содержат **21 наблюдение выбранного профиля на семи вопросах**, прошедшее отдельное содержательное ревью. Задание выполнено в проверенной области; новый live-прогон необязателен.

## Выбранная конфигурация

| Настройка | Baseline | Выбранная |
|---|---:|---:|
| Модель | Qwen2.5 14B Instruct | Qwen2.5 14B Instruct |
| Квантование | Q4_K_M | Q4_K_M; отдельно сравнивалось с Q5_K_M |
| Temperature | 0 | 0 |
| Максимум выходных токенов | 2048 | 1024 |
| Окно контекста (`num_ctx`) | 16384 | 8192 |
| Prompt / контракт ответа | Общие фактические утверждения | Справочные ответы V3; выбор доказательств процедуры V7 |

[SELECTED_PROFILE.json](SELECTED_PROFILE.json) фиксирует область применения, параметры, шаблоны, launcher и файлы доказательств. `max_tokens` — лимит ответа в приложении; provider передаёт его в Ollama как `num_predict`.

Retrieval использует индекс Недели 6 / [Дня 21](../day-21-document-indexing/README.ru.md): локальные `bge-m3`, fixed chunks, candidate K=20, final K=5, cosine threshold 0.50, heuristic rewrite и ограничение retrieval-контекста в 16000 символов. База открывается только для чтения.

В [profiles.json](profiles.json) есть варианты температуры, но её отдельный эффект на качество не измерялся. Лимиты ответа/контекста и prompt менялись совместно. Веса модели не дообучались.

## Как работает V7

Текущий launcher — **`experiments/quality_v7/main.py`**. Он сохраняет справочный шаблон V3 и направляет поддерживаемые вопросы о проверке периодического worker в selector-contract V7. Корневой `main.py` сохраняет исходный экспериментальный CLI и автоматически V7 не включает.

Для периодической процедуры:

1. Локальный retrieval получает фрагменты источников и точные цитаты.
2. Приложение разделяет доказательства по четырём ролям: статус сервиса, журнал, результат выполнения и повторение относительно расписания.
3. Локальная Qwen выбирает разрешённый ID для каждой роли либо отказывается, используя ограниченную JSON Schema.
4. Приложение проверяет IDs, роли, метаданные источника и точные подстроки, затем собирает источниковый план наблюдения.
5. Offline-аудит проверяет явные правила; отдельное содержательное ревью оценивает ответ по источникам.

`generation.answer` сохраняет сырые выборы модели. `response.answer` — процедура, собранная приложением. Приложение не выполняет показанные VPS-команды и не доказывает работу конкретного VPS. Другие процедуры не входят в подтверждённую область V7.

Неизвестный ID, неподходящая роль, пропущенный этап или подмена доказательства блокируют публикацию фактической процедуры. Законченные плохие ответы сохраняются как неудачные результаты; скрытых повторов до PASS нет. Runtime не вызывает облачный fallback или дополнительную аудиторскую LLM.

## Качество до и после

| Этап | Наблюдаемое поведение / результат ревью |
|---|---|
| Исходный ответ о worker | Называет `worker.py`, но добавляет лишние VPS-инструкции и неподтверждённую привязку цитаты |
| V3: справка / отрицательные контроли | Четыре вопроса × три ответа: **12/12 PASS** |
| V6: периодическая процедура | Более точные привязки, но неверный язык, установочные команды и неполная проверка повторений: **3/3 FAIL** |
| V7: исходный русский вопрос о процедуре | **3/3 PASS**; статус, журнал, выполнение и повторное сохранение разделены |
| Frozen transfer V7: новый английский вопрос | **3/3 PASS** |
| Frozen transfer V7: новый русский вопрос | **3/3 PASS** |

Итоговая область включает четыре справочных/отказных вопроса и три формулировки одного процедурного кейса. Сохранены все три наблюдения каждого опыта. В каждой тройке новых transfer-вопросов показанные ответы одинаковы. Код и transfer-вопросы были зафиксированы до проверки переноса.

Содержательное ревью выполнял ассистент по предоставленным JSON и исходной документации; оценки сохранены отдельно в `review/`. Автоматические проверки и точные цитаты сами по себе не подтверждают смысловую полноту. Исходные отчёты, неудачные ответы и автоматические вердикты не переписаны.

## Скорость, квантование и ресурсы

| Вопрос / вариант | Медиана генерации |
|---|---:|
| Факт о worker, baseline | 26.281 с |
| Факт о worker, Q4 / V3 | 6.091 с |
| Факт о worker, Q5 / V3 | 7.665 с |
| Периодическая VPS-процедура, V6 | 16.572 с |
| Периодическая VPS-процедура, V7 | 6.077 с |
| Новая английская формулировка V7 | 6.067 с |
| Новая русская формулировка V7 | 6.105 с |

V6→V7 снижает медиану этой процедуры примерно на **63.3%**, одновременно меняя вход и контракт ответа. 75 выходных токенов V7 — выборы доказательств; полный текст процедуры собирает приложение. Это не измерение ускорения свободной генерации одинакового ответа.

Первый transfer-ответ занял 13.496 с на английском и 12.637 с на русском; последующие — около 6 с. На время влияют prefill и prompt/KV-cache. Новые baseline и Q5 для transfer-набора не запускались.

Q4/Q5 сравнивались на **одном фактическом вопросе о worker**, по три наблюдения каждой версии, с одинаковыми настройками, messages и доказательствами:

| Метрика | Q4_K_M | Q5_K_M |
|---|---:|---:|
| Медиана генерации | 6.09 с | 7.66 с |
| Медиана decode | 11.47 tokens/s | 9.27 tokens/s |
| Максимальная Ollama `size_vram` | 9.56 GiB | 10.89 GiB |

Качество на этом вопросе равноценное; Q5 потребовал примерно на 25.8% больше времени и сообщил на 1.33 GiB больше аллокации. Q4 измерялся первым, порядок не рандомизирован. Преимущество на других задачах этим не установлено.

В полном контрольном отчёте максимум `size_vram` составляет 11.19 GiB для baseline и 9.67 GiB для выбранного профиля. Также сохранены выборочные RSS/CPU процессов, доступная системная память и swap. **RSS и `size_vram` не равны полной физической unified memory и не складываются.** Полный физический пик и GPU utilization не измерены.

Подробные сравнения и ограничения — в [FINAL_REPORT.ru.md](FINAL_REPORT.ru.md).

## Проверка сохранённого результата без Ollama

Из **корня репозитория**, с сохранёнными папками предыдущих дней:

```bash
python day-29-local-llm-optimization/experiments/quality_v7/main.py verify \
  day-29-local-llm-optimization/reports/check/control-v7.json

python day-29-local-llm-optimization/experiments/quality_v7/main.py verify \
  day-29-local-llm-optimization/reports/check/quality-transfer-v7.json
```

Команды проверяют seals отчётов, наблюдения, пересобранные ответы и сводки без обращения к Ollama и без исходной базы индекса. Они не генерируют ответы и не повторяют содержательное ревью. Для V7-отчётов используй launcher V7.

`consistent=true` подтверждает внутреннюю согласованность. В сохранённых отчётах могут оставаться **`optimization_verified=false` и `human_review_required=true`**: исходные консервативные автоматические поля сохранены. Отдельное содержательное ревью не записывается поверх вердикта в sealed-отчёте.

## Необязательный новый локальный эксперимент

Сохрани рядом Дни 21, 23, 26 и 28: Day 29 импортирует их индекс, retrieval и provider-компоненты. Используй окружение проекта на Python 3.13:

```bash
python -m pip install -r day-29-local-llm-optimization/requirements.txt
ollama pull bge-m3
ollama pull qwen2.5:14b
```

Достаточно уже работающего Ollama desktop server. Облачный ключ не нужен. Q5 требуется только для отдельного эксперимента с квантованием.

Корневые README входят в индексируемый корпус. **После их замены пересобери индекс перед следующим live-прогоном**:

```bash
python day-21-document-indexing/main.py build
python day-21-document-indexing/main.py verify
```

Пересборка меняет identity индекса; прежние кешированные ответы остаются историческими результатами, а не свежими замерами нового корпуса. Проверка сохранённых отчётов выше доступна без пересборки.

Посмотреть план выбранного профиля без модельных вызовов:

```bash
python day-29-local-llm-optimization/experiments/quality_v7/main.py plan \
  --profiles focused-v3-q4 --split all --case base-10
```

Проверить установленную модель и текущий индекс, затем при необходимости получить до трёх новых оцениваемых ответов:

```bash
python day-29-local-llm-optimization/experiments/quality_v7/main.py doctor \
  --profiles focused-v3-q4

python day-29-local-llm-optimization/experiments/quality_v7/main.py run \
  --profiles focused-v3-q4 --split all --case base-10 \
  --max-new-observations 3 \
  --output day-29-local-llm-optimization/reports/check/readme-live.json
```

`doctor` обращается к локальной Ollama, но не генерирует ответы. `run` может выполнять отдельно учтённые warmups и token probes; лимит оцениваемых ответов не ограничивает эти вызовы. Совпадающие законченные пробы переиспользуются, включая quality failures. Просмотри созданный аудит и проверь каждый ответ по источникам.
