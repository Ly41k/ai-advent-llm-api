# День 26 — локальная LLM и сравнение с облачной

Бублик отвечает через два провайдера с общим интерфейсом:

- **local** — скачанная модель `qwen2.5:7b` через Ollama на этом компьютере;
- **cloud** — `openai/gpt-oss-20b` через Groq, как в ранних днях курса.

Можно использовать уже установленную `qwen2.5:14b`, `llama3.2` или другую локальную chat-модель через `--local-model`. Модуль работает самостоятельно: база `knowledge.db`, embeddings, MCP и код Дня 25 не требуются.

## Что использовано из предыдущих дней

| Опыт | Применение в Дне 26 |
|---|---|
| Дни 1–2 | System/user messages, HTTP API, заданный формат ответа |

Это применение подходов из курса, а не подключение полного RAG-чата. Третий пример получает готовый фрагмент README; retrieval, embeddings и coverage-аудитор Дня 24 здесь не запускаются.

## Профиль v1.3: модель и калькулятор

В примере `calculation` приложение заранее вызывает `calculate_energy` с заданными входами. Python вычисляет число циклов, расход и остаток через целочисленную арифметику; фактический результат передаётся модели для формирования JSON. Отчёт сохраняет имя инструмента, входы и результат в `source`. Обе модели получают одинаковый контекст.

Здесь применён принцип MCP-дней: точные вычисления выполняет инструмент. Сам MCP не подключён, инструмент выбирает и вызывает приложение заранее; модель получает результат в пользовательском сообщении. Это **не проверка самостоятельной арифметики LLM**. Результат модели всё равно валидируется; неправильный JSON или изменённые числа остаются FAIL. Произвольный Python-код модели не выполняется.

Сохрани исходные отчёты v1.1/v1.2 отдельно: в них Qwen самостоятельно ошиблась в расходе энергии. Новые результаты v1.3 относятся к другому, assisted-профилю и не заменяют эти наблюдения. 38 offline-тестов прошли на Python 3.12; реальный запуск v1.3 на Mac также подтверждён предоставленным автором отчётом, см. результаты ниже.

## Быстрый запуск на Mac

Команды выполняются из корня репозитория либо из распакованного каталога поставки. Python 3.13 — целевой вариант проекта; модуль и тесты также проверены на Python 3.12.

```bash
source .venv/bin/activate
# Если venv ещё нет:
# python3.13 -m venv .venv
# source .venv/bin/activate

# Пропусти установку Ollama, если он уже установлен.
brew install --cask ollama
open -a Ollama
ollama --version
ollama pull qwen2.5:7b
ollama list

# Прямое обращение через CLI:
ollama run qwen2.5:7b "Чему равно 2 + 2? Ответь одним числом."

# Проверки Python-модуля без реальных LLM и без API-ключа:
python day-26-local-llm/test_day26.py -v

# Проверка API и установленной модели (без генерации):
python day-26-local-llm/main.py doctor

# Три реальных локальных запроса:
python day-26-local-llm/main.py demo --provider local \
  --output day-26-local-llm/reports/check/local.json
```

Если приложение Ollama не запущено, можно выполнить `ollama serve` в отдельном терминале. Если приложение уже обслуживает порт 11434, второй сервер запускать не нужно. Если `ollama` не находится после установки, открой новый терминал и проверь наличие CLI в установленном приложении Ollama.

Для уже установленной модели:

```bash
python day-26-local-llm/main.py demo --local-model qwen2.5:14b \
  --output day-26-local-llm/reports/check/local-14b.json
```

## Прямой HTTP-запрос

```bash
curl --fail-with-body http://127.0.0.1:11434/api/chat \
  -H 'Content-Type: application/json' \
  -d '{"model":"qwen2.5:7b","messages":[{"role":"user","content":"Чему равно 2 + 2? Ответь одним числом."}],"stream":false,"options":{"temperature":0,"num_predict":128}}'

# После генерации модель должна быть видна среди загруженных:
curl --fail-with-body http://127.0.0.1:11434/api/ps
ollama ps
```

Python-адаптер обращается только к loopback HTTP URL, отклоняет cloud-теги и remote-модели, обнаруженные через `/api/show`, и сохраняет `/api/ps` после генерации. Для наглядного подтверждения автономности заранее скачай модель, отключи интернет и повтори локальный `demo`; облачный `compare` выполняй после восстановления сети. Loopback адрес сам по себе не доказывает отсутствие проксирования произвольным сторонним сервером; здесь подразумевается обычная локальная установка Ollama.

## Облачная LLM и сравнение

Используется существующий `GROQ_API_KEY` из окружения или `.env` в корне репозитория. Для чтения `.env` нужен `python-dotenv`, который уже есть в корневых зависимостях курса:

```bash
python -m pip install -r day-26-local-llm/requirements.txt
# Если root .env уже содержит действующий GROQ_API_KEY, создавать новый не нужно.
# Иначе скопируй .env.example в .env и заполни GROQ_API_KEY в редакторе.

python day-26-local-llm/main.py doctor --provider cloud

# Три запроса только в Groq:
python day-26-local-llm/main.py demo --provider cloud \
  --output day-26-local-llm/reports/check/cloud.json

# Те же три запроса в Ollama и Groq: всего шесть генераций.
python day-26-local-llm/main.py compare \
  --output day-26-local-llm/reports/check/compare.json
```

Облачные режимы отправляют промпты в Groq и расходуют API-квоту. Local не требует ключа и не переключается на облако при ошибке. `compare` запускает провайдеры последовательно и сохраняет ошибки каждого, включая частично успешное сравнение. Повторных автоматических API-запросов нет.

## Три запроса разной сложности

| ID | Уровень | Задача | Автоматическая проверка |
|---|---|---|---|
| `simple` | Простой | 2 + 2, ответ одним числом | Ровно `4` |
| `calculation` | Средний | Энергобюджет через Python-калькулятор: 3600, активация 1200, цикл 400 | JSON: `cycles=6`, `total_cost=3600`, `remaining=0`; все значения целочисленные |
| `grounded_json` | Сложный | Извлечь сведения о worker Дня 18 и дословную цитату | 5 полей, правильные метрики/каналы, точное совпадение цитаты |

Полные промпты можно показать без сетевых вызовов:

```bash
python day-26-local-llm/main.py examples
```

Контекст сложного примера лежит в `fixtures/day18-context.json`. Это зафиксированный фрагмент `day-18-scheduled-mcp/README.md`, строки 5–17, commit `3db748323dadf8e863d0106ddec5b804ce66c953`. Он сохраняет происхождение текста; изменения текущего README не обновляют fixture автоматически. Тест проверяет совпадение при наличии соседнего Дня 18.

Каждый запрос изолирован: один и тот же system prompt и одно user message. Ответ предыдущего примера не попадает в следующий. В сравнении сохраняется SHA-256 каждого набора сообщений, чтобы проверить равенство входов.

## CLI и настройки

Опции ставятся **после подкоманды**:

```bash
python day-26-local-llm/main.py ask "Объясни разницу между локальной и облачной LLM в трёх предложениях." --provider local
python day-26-local-llm/main.py ask "Объясни разницу между локальной и облачной LLM в трёх предложениях." --provider cloud
python day-26-local-llm/main.py ask "Чему равно 12 × 13?" --provider both --output day-26-local-llm/reports/check/custom.json

python day-26-local-llm/main.py compare --local-model qwen2.5:14b \
  --cloud-model openai/gpt-oss-20b --timeout 300 --max-tokens 4096
```

| Настройка | По умолчанию | Значение |
|---|---|---|
| `--provider` | `local` | `local`, `cloud`, `both`; compare всегда both |
| `--local-model` | `qwen2.5:7b` | Имя скачанной модели Ollama |
| `--cloud-model` | `openai/gpt-oss-20b` | Доступная chat-модель Groq |
| `--url` | `http://127.0.0.1:11434` | Локальный API Ollama |
| `--temperature` | `0` | Передаётся обоим провайдерам |
| `--max-tokens` | `2048` | Ollama `num_predict`, Groq `max_completion_tokens` |
| `--num-ctx` | `8192` | Контекст локальной модели |
| `--timeout` | `180` | Таймаут одного HTTP-вызова в секундах |
| `--output` | Не задан | JSON и соседний Markdown для demo/compare/ask; doctor пишет только JSON |

`OLLAMA_MODEL` и `GROQ_MODEL` можно задать в окружении процесса; CLI имеет приоритет. `.env` загружается только для получения облачного ключа. Для GPT-OSS в Groq используется `reasoning_effort=low`; это не идентичный режим рассуждения Qwen. Числа лимитов и token usage не означают одинаковый объём видимого текста у разных моделей.

## Как читать результат

Генерации сохраняют ответы, latency, token usage, finish reason, проверки и контекст с source metadata. Локально дополнительно записываются время загрузки, время генерации, decode tokens/s и список загруженных моделей. Ключ и HTTP Authorization headers в отчёты не записываются.

- `status=ok`: непустой ответ с нормальным завершением `stop`;
- `status=incomplete`: ответ получен, но генерация не завершилась штатно, например `length`;
- `status=error`: ошибка настройки, HTTP или ответа провайдера;
- `check.passed`: проверка ответа на конкретный пример;
- `local_launch_verified`: есть штатный локальный ответ и модель видна в `/api/ps`;
- `day26_local_three_requests_verified`: все три встроенных локальных запроса ответили штатно, модель видна в `/api/ps`;
- `all_checks_passed`: все проверки ответов пройдены.

Модель может пройти проверку запуска и ошибиться в JSON: эти результаты различаются намеренно. Для `ask` проверяется только штатное завершение; содержимое оценивается вручную. Код завершения 0 означает успешные проверки, 1 — ошибку/неполную генерацию/неверный ответ/неподтверждённую локальную загрузку, 2 — некорректные аргументы CLI.

Сравнение оценивает **модель вместе с окружением**: HTTP latency включает загрузку локальной модели, сеть и обработку облачного запроса. Token counts используют разные токенизаторы; `tokens_per_second` локально считается по `eval_duration`, а не по HTTP latency. Неизвестные метрики — `null`. Денежная стоимость локального вычисления не объявляется нулевой и не оценивается автоматически. Повтори запуск отдельно, если нужно сравнить первый запрос и запрос к уже загруженной модели.

## Проверка задания и запись видео

Для установленной `qwen2.5:14b`:

```bash
ollama --version
ollama list
python day-26-local-llm/main.py compare --local-model qwen2.5:14b \
  --output day-26-local-llm/reports/video/compare-video.json
ollama ps
```

`compare` выполняет три локальных и три облачных запроса. В консоли печатаются ответы, PASS/FAIL и итоговая сводка; полные промпты, source и метрики доступны в JSON. Поясни, что средний пример использует расчёт Python. Для демонстрации только обязательной локальной части замени `compare` на `demo --provider local`, сохранив остальные опции; облачный ключ тогда не нужен.

Покажи `local_launch_verified=true` и `day26_local_three_requests_verified=true`. Успех всех проверок обозначается `all_checks_passed=true`, но корректность ответа и факт работающей модели — разные проверки. `doctor` без генерации недостаточен для сдачи.

Файлы под `reports/check/` и `reports/video/` игнорируются Git. После ручного просмотра можно сохранить успешный отчёт для коммита:

```bash
mkdir -p day-26-local-llm/reports/live
cp day-26-local-llm/reports/check/compare-v1.3.json day-26-local-llm/reports/live/
cp day-26-local-llm/reports/check/compare-v1.3.md day-26-local-llm/reports/live/
```

Укажи фактический путь к своему отчёту, если он другой. `.env.example`, код, тесты, fixture, README и отобранные отчёты добавляются в Git; настоящий `.env`, `.venv` и `__pycache__` остаются локально. Не показывай ключ в видео.

## Offline-проверка

38 offline-теста на Python 3.12 проверяют настоящие HTTP-вызовы к тестовому серверу, payload обоих провайдеров, одинаковые промпты, отчёты, JSON/цитаты, ошибки HTTP, запрет redirects, таймауты, пустые и обрезанные ответы, отсутствие скрытого cloud fallback.

Offline-тесты проверяют код и не заменяют запуск модели. Реальные ответы ниже получены автором на Mac и проверены по предоставленному `compare-v1.3.json`; это отдельная проверка от тестов.
