# День 18: пошаговая проверка

Команды ниже выполняйте **из корня распакованного `ai-advent-llm-api`**. Рекомендуется Python 3.13 (версия проекта) и интернет до `api.github.com`. `GROQ_API_KEY` для шагов 1–7 не нужен. Команды для macOS/Linux; в Windows замените `.venv/bin/python` на `.venv\\Scripts\\python.exe`.

## 1. Установите зависимости

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r day-18-scheduled-mcp/requirements.txt
```

## 2. Прогоните автоматические проверки

```bash
.venv/bin/python day-18-scheduled-mcp/test_day18.py -v
```

Ожидается `OK`. Тесты проверяют реальный MCP stdio-вызов, сохранение расписания в SQLite, два запуска по времени, агрегацию, повтор после ошибки и ответ агента с данными инструмента. Здесь используются fake GitHub API и fake LLM; настоящие ключ и сеть не требуются.

## 3. Создайте расписание **через MCP**

```bash
.venv/bin/python day-18-scheduled-mcp/mcp_cli.py schedule Ly41k ai-advent-llm-api 1
```

Ожидается JSON с `interval_minutes: 1` и `next_run` в UTC. Инструмент создаёт файл `day-18-scheduled-mcp/schedule.db`. Первый сбор назначен сразу, затем — каждую минуту. CLI действительно вызывает `schedule_github_summary` по MCP: он не записывает SQLite напрямую.

Интервал `1` минута используется только для быстрой проверки периодического выполнения. После завершения проверки на VPS рекомендуется переключить
расписание на более редкий рабочий интервал, например 15 минут.

> Если у вас уже была база с этим заданием, повторная команда обновит интервал и начнёт новую минуту. Для полностью чистого опыта можно переименовать `schedule.db` перед шагом 3; не делайте этого, если хотите сохранить старые снимки.

## 4. Запустите отдельный worker

В первом терминале:

```bash
.venv/bin/python day-18-scheduled-mcp/worker.py
```

В течение примерно 15 секунд ожидается JSON с `status: "ok"` и `summary.samples >= 1`. Убедитесь, что `summary.latest` содержит `stars`, `forks` и `open_issues`. Если увидите `status: "error"`, прочитайте `detail`: для этого шага нужен доступ к GitHub API.

## 5. Запросите агрегат через MCP

Во втором терминале:

```bash
.venv/bin/python day-18-scheduled-mcp/mcp_cli.py summary Ly41k ai-advent-llm-api
.venv/bin/python day-18-scheduled-mcp/mcp_cli.py jobs
```

В первой команде ожидаются `samples`, `latest`, `change`, `from`, `to`, `next_run`. После первого сбора `samples: 1`, все значения `change` равны нулю. Во второй команде есть сохранённое задание и время следующего запуска.

## 6. Проверьте повторное выполнение **по реальному времени**

Оставьте worker работающим минимум на 75 секунд после первого вывода. Ожидается второй JSON с `status: "ok"`; повторите `mcp_cli.py summary ...`. Теперь `samples >= 2`. `change` — разница между последним и самым старым из выбранных снимков; она может остаться нулевой, если показатели GitHub не изменились. Ключевой показатель периодичности — увеличение `samples` и сдвиг `to`/`next_run`.

## 7. Проверьте сохранение после перезапуска

Остановите worker с `Ctrl+C`. Снова выполните команду `mcp_cli.py summary ...`: снимки и задание должны сохраниться. Запустите worker повторно, дождитесь следующего запуска и проверьте рост `samples`. Если время `next_run` ещё не наступило, worker подождёт; если наступило во время простоя, выполнит задание один раз.

Файл `schedule.db` хранится локально и не входит в исходный архив. `BUBLIK_DB_PATH=/абсолютный/путь/к/schedule.db` позволяет задать иной путь, но **одинаковый** для MCP CLI, агента и worker.

## 8. Проверьте сам агент (нужен Groq key)

Создайте `.env` **в корне репозитория**, содержащий `GROQ_API_KEY=...`, затем:

```bash
.venv/bin/python day-18-scheduled-mcp/main.py
```

Спросите: «Покажи сохранённую сводку Ly41k/ai-advent-llm-api». Ожидается ответ Бублика с цифрами сводки и строка `[MCP] get_github_summary ...`. Если модель не выбрала инструмент, повторите с явным указанием `get_github_summary`; автоматические тесты подтверждают работу цикла при вызове инструмента, но самостоятельный выбор инструмента моделью зависит от внешнего API.

## 9. Проверьте работу 24/7 на VPS

Подставьте реальные пользователя и пути в `day-18-scheduled-mcp/bublik-day18.service.example`, затем скопируйте конфигурацию в `/etc/systemd/system/bublik-day18.service`. Убедитесь, что пользователь сервиса имеет право записи в каталог базы и исходящее соединение к `api.github.com`. Создайте расписание на VPS командой из шага 3. Если используете `BUBLIK_DB_PATH` из unit, выставьте ту же переменную при запуске MCP CLI.

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now bublik-day18
systemctl is-active bublik-day18
journalctl -u bublik-day18 -f
```

Ожидается `active` и новая сводка в журнале каждый интервал. Для проверки восстановления сервиса: `sudo systemctl restart bublik-day18`, затем `systemctl is-active bublik-day18` и `mcp_cli.py summary ...`. Для проверки переживания перезагрузки VPS: после планового reboot снова проверьте статус и журнал. **До этих проверок на вашем VPS нельзя утверждать, что работа 24/7 там подтверждена.**

После проверки минутного интервала переключите расписание на более спокойный рабочий режим, например 15 минут:

```bash
.venv/bin/python day-18-scheduled-mcp/mcp_cli.py \
    schedule Ly41k ai-advent-llm-api 15

.venv/bin/python day-18-scheduled-mcp/mcp_cli.py jobs

## Что именно выдаётся автоматически

Работающий по расписанию процесс выводит структурированную агрегированную сводку в терминал или журнал systemd. Интерактивный Бублик прочитает её через MCP и сформулирует ответ, когда вы спросите. Автоматической отправки сообщений в Telegram, почту или этот чат в Дне 18 нет.
