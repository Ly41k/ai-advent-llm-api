# День 23 — Фильтрация релевантности и query rewrite

Реальные пользовательские прогоны `bge-m3` / `llama3.2` / `qwen2.5:7b`, повторная сверка задания и ограничения: [LIVE_VERIFICATION.ru.md](LIVE_VERIFICATION.ru.md). Исследовательский профиль fixed/20/5/0.50 сохраняет ожидаемые документы и сокращает контекст; ошибки генерации и выбор порога после просмотра evaluation отмечены явно. Кодовые defaults сохранены, профиль задаётся CLI-флагами.

Продолжение Дней 21–22: используем ту же SQLite-базу знаний и локальный Ollama. Второй этап после поиска — **фильтр по исходной cosine similarity**. Это один из разрешённых заданием вариантов вместо отдельного reranker. Новые Python-зависимости не нужны.

`исходный вопрос → необязательный rewrite → embedding → top-K кандидатов → порог релевантности → итоговый top-K → исходный вопрос + выбранный контекст → LLM`

| Режим | Rewrite | Фильтр |
|---|---|---|
| `baseline` | Нет | Нет |
| `filter` | Нет | Да |
| `rewrite` | Да | Нет |
| `rewrite_filter` | Да | Да |

По умолчанию: **20 кандидатов → cosine >= 0.35 → максимум 5 чанков**. Порог включительный: значение, равное порогу, проходит. Используется `Hit.score`, а не отображаемое `(cosine+1)/2`; similarity не является вероятностью правильного ответа. Порог `0.35` — стартовая настройка, его нужно подобрать на своём индексе. После фильтра может остаться меньше пяти чанков или ни одного. При пустом контексте возвращается отказ без вызова answer-модели и без восстановления отброшенных результатов.

## 2. Увидеть поиск и сравнить ответы

```bash
python day-23-reranking-filtering/main.py search \
  "На 18 дне кто выполняет фоновые джобы по расписанию?"

python day-23-reranking-filtering/main.py compare \
  "На 18 дне кто выполняет фоновые джобы по расписанию?" \
  --output day-23-reranking-filtering/compare_results.json

python day-23-reranking-filtering/main.py \
  --candidate-k 30 --final-k 4 --min-similarity 0.25 \
  ask "How does the Day 18 worker run?" --mode filter
```

Глобальные параметры стоят **до** `search/ask/compare/evaluate/calibrate`. `search` не генерирует ответ, `ask` запускает один режим, `compare` — четыре. В JSON видны исходный и поисковый вопросы, кандидаты, score, причины отсечения, итоговые источники и полный контекст.

## 3. Query rewrite

По умолчанию работает `heuristic`: небольшой общий словарь расширяет технические сокращения и русские слова поисковыми терминами. Сохраняется исходная строка, номера дней, идентификаторы и отрицания. Rewrite не получает gold answers и не подставляет готовый ответ.

Можно включить отдельный вызов локальной модели:

```bash
python day-23-reranking-filtering/main.py --rewrite-method llm \
  compare "Как на 16 дне клиент узнаёт доступные инструменты МСП?"
```

LLM предлагает поисковое расширение; пустой или слишком длинный результат заменяется исходным вопросом. Ошибки соединения не скрываются. Исходный вопрос всегда используется при генерации ответа. В `compare` rewrite выполняется один раз, а режимы с фильтром и без него получают одни и те же кандидаты для соответствующего поискового запроса. Модель, prompt и temperature=0 одинаковы во всех четырёх режимах. Повторная генерация по одному чанку из Дня 21 здесь не используется, чтобы не влиять на сравнение.

## 4. Подобрать порог и проверить качество

Набор: **20 вопросов**, из них 10 исходных контрольных вопросов Дня 22, шесть разговорных вопросов и четыре вопроса без ответа в корпусе. **8 вопросов — calibration, 12 — evaluation**.

```bash
python day-23-reranking-filtering/main.py calibrate
```

Открой `calibrate_results.json` и найди `selected_threshold`. Калибровка использует только восемь calibration-вопросов, переиспользует найденные кандидаты и не генерирует ответы. Сначала исключаются пороги, которые ухудшают попадание правильного источника или увеличивают пустые ответы на положительных calibration-вопросах относительно режима `rewrite`. Среди оставшихся выбирается лучший баланс попадания источников и отказа на отрицательных вопросах; при равенстве учитываются precision и более низкий порог. Если подходящего порога нет, добавь более низкие значения:

```bash
python day-23-reranking-filtering/main.py calibrate \
  --thresholds 0 0.05 0.1 0.15 0.25 0.35
```

Дальше подставь **свой** найденный порог. `0.25` ниже — только пример:

```bash
python day-23-reranking-filtering/main.py --min-similarity 0.25 evaluate
python day-23-reranking-filtering/main.py --min-similarity 0.25 evaluate --retrieval-only
```

По умолчанию `evaluate` проверяет только 12 evaluation-вопросов. В `evaluate_results.json` — ответы четырёх режимов, переписанные запросы, точный контекст, источники, все решения по кандидатам, метрики и разницы между режимами. В `.md` — таблица. `--split all` полезен для осмотра, но смешивает вопросы подбора и проверки.

Измеряем document source-hit, precision по размеченным источникам, MRR, отказ на вопросах вне корпуса, потерю контекста на положительных вопросах, объём контекста и покрытие ожидаемых терминов. **Это диагностика, а не доказательство смысловой правильности.** Разметка может не перечислять другие подходящие документы. Вручную заполни `human_review`: релевантность чанков, подтверждение ответа контекстом, правильность относительно ожидания; 0 — плохо, 1 — частично, 2 — хорошо. На маленьком наборе возможен переобученный порог: уменьшение контекста нельзя само по себе считать улучшением.

`--retrieval-only` отключает генерацию ответов. При `--rewrite-method llm` вызов модели для rewrite всё равно остаётся; полностью без generation используй стандартный `heuristic`.

## 5. Демонстрация без Ollama

```bash
python day-23-reranking-filtering/offline_demo.py
```

Программа строит временный реальный SQLite-индекс по текущим файлам корпуса, используя явно обозначенный **лексический TF-IDF hash embedder**. Подбирает порог на восьми вопросах и проверяет двенадцать остальных. JSON и Markdown находятся в `reports/offline_*`.

Это выполненная проверка retrieval-механизма, **без генерации или имитации LLM-ответов**. Она не измеряет качество `bge-m3`/`llama3.2`, а её порог нельзя переносить на эти модели. В примере rewrite помогает некоторым запросам, а фильтр может ухудшить recall на отложенных вопросах — в отчёте сохранены и улучшения, и ухудшения.

Тесты отдельно проверяют полный путь CLI → локальный HTTP-контракт Ollama → SQLite → контекст → ответ → JSON/Markdown на заглушке. Реальный модельный прогон выполняется приведёнными выше командами на Mac.
