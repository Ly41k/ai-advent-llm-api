# Исправление разрешения повторного вопроса v4

В followup-v3.json planner вернул исходное «А где это хранится?» и needs_clarification=true. Память сохранилась и лишних обновлений не было, но предмет вопроса не раскрылся. Свежий поиск получил вопрос без предмета: 20 кандидатов, ноль после порога 0.50. Выбор цитат и coverage не вызывались; причина ответа — ambiguous_reference.

Промпт v3 не устранил проблему передачи истории: прежний recent_context передавал только исходную реплику и начало ответа. В следующее разрешение не попадал ранее принятый resolved_question. Поэтому отказ мог скрыть полезную интерпретацию предыдущего вопроса.

## Изменения

- В bounded history передаются ранее принятый resolved_question, answer_status, признак принятия разрешения и отпечаток значений task state. Ограничения размера истории сохранены.
- Отказ по источникам/полноте не отменяет отдельно принятое разрешение темы.
- Только для одинаковых вопросов подряд, с неизменившимися значениями памяти, приложение может повторно использовать ранее принятую самостоятельную формулировку. История просматривается назад лишь до первого другого вопроса. Неоднозначный повтор не стирает ранее раскрытую тему в этой цепочке.
- Изменение цели, ограничения, уточнения или термина отменяет такое повторное использование. Новой самостоятельной теме разрешение старого вопроса не навязывается.
- Исходный ответ planner остаётся в raw; повторное использование видно в conversation.resolution_reused. Это интерпретация вопроса, не факт и не семантическая гарантия модели.
- Поиск, выбор цитат и строгий coverage всегда выполняются заново. Ответы, найденные чанки и положительный verdict не переиспользуются.
- Работает с уже сохранёнными response JSON; миграция chats.db не нужна. Формат task state не меняется.

Полностью неоднозначный вопрос без известной формулировки сохраняет отказ. Строгие проверки доказательств, порог и Python-модули дней 21–24 не изменены.

## Проверка

40 тестов дня 25 прошли, включая два технических сценария по 12 ходов. Три новых теста проверяют передачу формулировки из ответа-отказа, отмену повторного использования при смене темы/памяти, повтор после отрицательного coverage с перезапуском SQLite и новым поиском.

Кроме того, выполнен replay настоящих пользовательских JSON: memory-turn.json → memory-turn-v2.json → followup.json → followup-v3.json. Использованы реальные state и прежний raw planner из followup-v3.json. Теперь он приводит к разрешённому вопросу «А где хранятся снимки, которые сохраняет worker на день 18?», effective_needs_clarification=false, память не меняется. Результат replay приложен в reports/verified/resolution-trace-replay.json.

Replay проверяет код разрешения, не качество настоящего Qwen при выборе цитат/coverage. Локальные интеграционные тесты используют scripted HTTP-стенд; живой ответ после v4 нужно проверить отдельно.

## Применение и повтор

Архив включает все предыдущие исправления v1–v3. Распаковать из корня репозитория. Базы/история не входят в архив; пересборка knowledge.db и восстановление памяти не нужны.

```bash
unzip -o ~/Downloads/day-25-resolution-fix-v4.zip
python day-25-rag-chat/test_day25.py -v
```

Ожидается Ran 40 tests и OK. Повторить тот же вопрос в прежней сессии:

```bash
python day-25-rag-chat/main.py ask \
"А где это хранится?" \
--session 2cb61350c3d54c218d260e6a5cd65969 \
--output day-25-rag-chat/reports/check/followup-v4.json
```

В trace ожидается разрешённый вопрос о снимках worker дня 18, новый retrieval и неизменная память. Ответ с источниками всё ещё зависит от реального selector/coverage. При отказе проверять его конкретную причину в followup-v4.json, не снижать порог и не менять strict policy для получения формального успеха.
