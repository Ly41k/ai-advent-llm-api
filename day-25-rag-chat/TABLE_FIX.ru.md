# Исправление чтения таблиц v6

В topic-switch.json новая тема правильно выбрана: вопрос о дне 20, свежий retrieval, 20 кандидатов, 5 выбранных чанков, первый — README.ru.md дня 20. Цель дня 18, два ограничения, оба уточнения и термин сохранены без изменений. Planner ошибочно отметил needs_clarification=true для самостоятельного вопроса; защита направила его в поиск. Warnings пусты.

Selector выбрал шесть фрагментов README, включая q1_3 — таблицу с серверами github, analysis, storage. Все выбранные фрагменты дословные. Coverage дважды заявил, что имена или полные пути не указаны, хотя p3_3, p3_4, p3_5 явно содержат имена в столбце «Сервер». Вопрос полного пути не запрашивал.

## Что изменено

- В дополнение к индексу имён аудитор получает индекс Markdown-строк: exact header/value, proof_id строки и header_proof_id.
- Индекс строится только из разрешённых proof units. Заголовок, разделитель и строки принадлежат одному claim; число столбцов должно совпадать. Пары header/value — дословные фрагменты исходных proof texts, роли не выдумываются.
- Индекс ограничен 16 строками и 4000 символами; недопустимая структура даёт пустой индекс, а не новое доказательство.
- Промпт объясняет связь колонок с типом перечисляемой сущности. Таблица с именами — допустимый источник ответа о составе, даже без дублирующего предложения в прозе.
- Селектору предлагается для простого перечисления выбирать таблицу/список и не добавлять целый сценарий исполнения или обработку ошибок. Явно запрошенные роли, пути, порядок и проверки остаются обязательными.

Состав серверов в код не зашит. Модель по-прежнему выбирает цитаты/proof IDs и самостоятельно оценивает полноту; отрицательный verdict остаётся отрицательным. Порог, строгая политика, модули дней 21–24, рабочие базы не изменены.

## Проверка

46 тестов дня 25 прошли, включая два технических сценария по 12 ходов. Новые тесты проверяют дословность заголовков/ячеек, границы schema и claim, обязательный разделитель, совпадение ширины, ограничение индекса, безопасную обработку некорректного ввода и сохранение отрицательного ответа аудитора.

На proof units из настоящего topic-switch.json индекс построен для github, analysis, storage со столбцом «Сервер» и ссылками p3_3, p3_4, p3_5 → p3_1. Реплей формирования входа приложен в reports/verified/table-trace-replay.json. Эти проверки не доказывают положительный ответ настоящего Qwen после v6; нужен живой повтор.

## Применение и повтор

Архив включает исправления v1–v5. Распаковать поверх корня проекта. Базы и историю не содержит; пересборка knowledge.db и миграция chats.db не нужны.

```bash
unzip -o ~/Downloads/day-25-table-fix-v6.zip
python day-25-rag-chat/test_day25.py -v
```

Ожидается Ran 46 tests и OK. Повторить исходный вопрос в прежней сессии:

```bash
python day-25-rag-chat/main.py ask \
"Какие MCP-серверы участвуют в оркестрации на день 20?" \
--session 2cb61350c3d54c218d260e6a5cd65969 \
--output day-25-rag-chat/reports/check/topic-switch-v6.json
```

Ожидаем ответ с тремя серверами и источником дня 20, свежий поиск, сохранение прежней памяти/цели. При повторном отказе проверять raw coverage и выбранные доказательства. Автоматические scripted тесты не заменяют проверку настоящей модели.
