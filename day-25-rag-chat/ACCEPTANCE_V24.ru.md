# Итоговая приёмка дня 25 на настоящей Ollama

## 1. Подготовка

Установите v24, выполните 181 тест и verify индекса по RELEASE_V24.ru.md. Оставьте настройки вашего работающего bge-m3 / qwen2.5:14b, strict coverage, fixed, cosine ≥0.50. Не меняйте модель/индекс/код посередине проверки. Смена embedding-модели требует build. Новую версию сначала проверяем, коммит после приёмки может сделать индекс stale.

## 2. Один новый прогон двух диалогов

В обычном терминале, а не в `You>`:

```bash
python day-25-rag-chat/main.py evaluate \
  --process-per-turn \
  --output day-25-rag-chat/reports/check/live-long-scenarios-v24.json
```

Автоматически создаются две новые сессии: scheduler и orchestration, по 12 вопросов. Каждый вопрос — новый CLI-процесс и свежий RAG. Всего 24 вопроса / 48 сообщений при успешных ответах. Живой прогон по-прежнему может длиться больше часа. Теперь отчёт сохраняется после каждого хода; незавершённый отчёт имеет `run_status=running`, общий PASS только после завершения.

При обычной остановке повторите **ту же команду и настройки**, добавив `--resume`. Уже сохранённые вопросы не вызывают модель повторно. Один завершённый ход, потерянный между SQLite commit и checkpoint, восстанавливается из истории. Изменившиеся настройки/сценарий/индекс или несовпадающая история вызывают явную ошибку.

После kill и сообщения о pending сначала найдите session ID в отчёте, откройте `python day-25-rag-chat/main.py chat --session ID`; внутри `You>` выполните `/history`, `/recover`, `/quit`. Recover не отменяет запрос живого владельца. Затем продолжите evaluate с `--resume`. Восстановленный технический error остаётся FAIL: продолжение экономит время и сохраняет диагностику, не превращает прерванный прогон в полностью чистый.

## 3. Проверка отчёта

Ожидаем `run_status=completed`, `summary.user_turns=24`, `summary.messages_including_answers=48`, `summary.restart_kind=process_per_turn`, `all_checks_pass=true`. Проверяем все per-turn flags, 24 разных PID и request ID, фактические embedding/search calls, оба полных экспорта/истории. В конце каждой сессии — правильная цель, два ограничения, уточнение и термин с исходным evidence/turn/origin. При detour остаётся старая цель, а поиск временно относится к новой теме.

`model_quality_verified=false` и `manual_source_review_required=true` намеренно сохраняются даже при автоматическом PASS. Это честное различие происхождения текста и смыслового качества ответа.

## 4. Ручной просмотр 24 ответов

Для каждого хода заполните `manual_review.relevant`, `complete`, `goal_respected` в копии отчёта или отдельной таблице. Исходный автоматический JSON не переписывайте ради зелёного результата. Сначала сравните `question` и `resolved_question`: сохранены все части, отрицания и актуальная тема. Затем сверьте опубликованные цитаты с файлами/строками, а не только с положительным auditor verdict. Факт из нецитированного соседнего текста не исправляет неполный ответ задним числом.

| Ход | Scheduler: обязательный смысл | Orchestration: обязательный смысл |
|---|---|---|
| 1 | Отдельный `worker.py` выполняет фоновые задания | Три сервера: github, analysis, storage |
| 2 | Сохраняются stars, forks, open_issues и время | Storage: save_report, read_report |
| 3 | Снимки/расписание хранятся в SQLite schedule.db | Analysis: summarize_repository, verify_report |
| 4 | Расписание создаёт schedule_github_summary | FETCH → SUMMARIZE → SAVE → READ → VERIFY; принадлежность серверам верна |
| 5 | Первый сбор назначен сразу | Полный отчёт завершён только при verified=true |
| 6 | Допустимый интервал расписания: 1–10080 минут | Сводка сравнивается с текстом, перечитанным из сохранённого файла |
| 7 | get_github_summary: количество снимков, последнее состояние, изменения относительно самого старого выбранного | Преждевременный VERIFY: агент выбирает допустимый следующий шаг и отмечает agent correction; не путать с HTTP400 fallback |
| 8 | list_scheduled_jobs: расписание, следующий запуск, ошибка | --task info: только GitHub |
| 9 | После простоя каждое просроченное задание выполняется один раз, без пачки пропущенных запусков | --task summary: GitHub + analysis, без сохранения |
| 10 | Автоматической отправки результатов worker в чат нет | Временный detour: worker дня 18; цель дня 20 и остальная память не меняются |
| 11 | Worker не требует Groq key; сетевой доступ GitHub нужен | Возврат к цели: mcp_registry.py регистрирует серверы, уникальные имена и маршрутизирует инструменты |
| 12 | stdout / systemd journal; журнал соответствует способу запуска | Для локального сценария дня 20 VPS и worker не нужны |

Источники соответствуют ожидаемому дню; для orchestration #10 — день 18. Условия/ограничения в цитате не обрезаны, Python/docstrings и таблицы не оборваны. Нет противоречащих маршрутов и фактов, пришедших только из памяти/старого ответа. Избыточный, но правильный фрагмент отмечаем как полировку; ложный отказ, пропущенный обязательный факт или перенос действия между условиями — FAIL.

## 5. Дополнительные отрицательные проверки

Два коротких запроса выполняйте после длинного прогона, отдельно от исходных 12+12:

```bash
python day-25-rag-chat/main.py ask \
  "А где это хранится?" \
  --output day-25-rag-chat/reports/check/ambiguous-v24.json

python day-25-rag-chat/main.py ask \
  "Сколько снимков прямо сейчас в моей локальной schedule.db дня 18 на MacBook? Назови точное число." \
  --output day-25-rag-chat/reports/check/unknown-local-v24.json
```

Ожидаем честный unknown/уточнение, новый RAG и блок источников без выдуманного источника/числа. Чат знает индекс репозитория, а не содержимое локальной базы дня 18. Для ambiguous без session новая сессия не имеет предмета прежней беседы.

Команды `/goal`, `/constraint`, `/clarify`, `/term`, `/state`, `/history`, `/export`, `/recover` вводятся только внутри `You>`. В zsh/bash используются `python ... main.py state/history/export ...`.
