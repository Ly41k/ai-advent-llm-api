# Исправление памяти v2

Пользовательский memory-turn.json выявил потерю уточнения. Planner вернул новое «Первый сбор проверяем вручную.» с ключом f561dcbbee5b, который уже принадлежал «Проверяем локальный запуск.». Старый update доверял выбранному моделью ключу и заменял запись. Значение нового уточнения действительно присутствовало в текущем сообщении, поэтому прежняя проверка evidence не обнаруживала ошибку.

Исправление сохраняет новые ограничения/уточнения под ключом, вычисленным из значения. Замена существующего значения разрешена только при явном запросе исправления и идентификации старой записи в текущем сообщении: её ключом или полным прежним значением. Иначе обе записи сохраняются. Корректировка ошибочного ключа остаётся в conversation.memory_adjustments, исходный JSON модели — в conversation.raw. Повторная запись того же значения сохраняет прежнее evidence/turn/origin. Изменение термина требует его имени в текущем evidence. Команды /goal, /constraint, /clarify, /term и /forget остаются явным управлением памятью.

Пример исправления обычным сообщением: `Заменить «Используем SQLite.» на «Используем PostgreSQL.»`. Если фраза не прошла консервативную проверку явного исправления, оба значения сохраняются; устаревшее удаляется /forget. Это защита от потери памяти, не семантический решатель противоречий.

## Проверка

35 тестов дня 25 прошли. Четыре новых теста покрывают:

- точный planner JSON из memory-turn.json, сохранение обоих уточнений, цели, ограничений и термина, новый поиск и перезапуск SQLite;
- неверный ключ ограничения и повторное подтверждение без изменения происхождения;
- явную коррекцию по старому значению/ключу и сохранение независимой записи при отсутствии запроса замены;
- защиту существующего термина от изменения без его имени.

Набор также включает два технических сценария по 12 ходов. Локально используется scripted HTTP-стенд; повторная проверка настоящего Qwen после этого патча ещё нужна. Ответ из пользовательского memory-turn.json имеет два опубликованных источника; все четыре цитаты совпали с соответствующими строками файлов репозитория. Retrieval: 20 кандидатов, 4 после порога, 4 выбрано. Ответ содержит нужные поля, но избыточные фрагменты остаются отдельным замечанием к качеству.

## Применение и повторная проверка

Архив включает предыдущий planner-fix-v1, поэтому его можно применять к исходному day-25-rag-chat-solution.zip или поверх v1. Распаковать из корня проекта; рабочие базы не входят в архив и не меняются. Пересборка knowledge.db не нужна. Модули дней 21–24 не изменены.

```bash
unzip -o ~/Downloads/day-25-memory-fix-v2.zip
python day-25-rag-chat/test_day25.py -v
```

Ожидается `Ran 35 tests` и `OK`. Патч предотвращает новые потери, но не восстанавливает автоматически ранее заменённое значение. Для пользовательской сессии из memory-turn.json вернуть известное старое уточнение:

```bash
python day-25-rag-chat/main.py chat --session 2cb61350c3d54c218d260e6a5cd65969 <<'BUBLIK_COMMANDS'
/clarify Проверяем локальный запуск.
/state
/quit
BUBLIK_COMMANDS
```

Затем повторить естественное уточнение и вопрос:

```bash
python day-25-rag-chat/main.py ask \
"Уточнение: Первый сбор проверяем вручную.
Какие поля входят в снимок, который сохраняет worker на день 18?" \
--session 2cb61350c3d54c218d260e6a5cd65969 \
--output day-25-rag-chat/reports/check/memory-turn-v2.json
```

В результате должны сохраниться цель, два ограничения, термин и ДВА уточнения. В ответе нужны источники. После этого проверить состояние отдельным процессом:

```bash
python day-25-rag-chat/main.py state 2cb61350c3d54c218d260e6a5cd65969
```

Предыдущий ошибочный ход сохраняется в истории для диагностики; патч её не переписывает.
