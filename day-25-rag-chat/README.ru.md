CLI-чат Бублика переиспользует текущий код дней 21–24. История диалога и память задачи сохраняются в отдельной SQLite-базе `day-25-rag-chat/chats.db`. Каждый обычный пользовательский вопрос запускает новый поиск по `day-21-document-indexing/knowledge.db`.

## Быстрый запуск

Команды из корня проекта; рекомендуется существующий Python 3.13 и `.venv`. Текущая версия рассчитана на macOS/Linux и локальную файловую систему (POSIX-блокировки). Базовый день 25 использует стандартную библиотеку Python, без дополнительных pip-пакетов и Groq key.

```bash
source .venv/bin/activate
python day-25-rag-chat/test_day25.py -v
python day-25-rag-chat/main.py offline-demo
```

Для настоящего чата Ollama должен работать локально:

```bash
ollama pull bge-m3
ollama pull qwen2.5:14b
python day-21-document-indexing/main.py build
python day-21-document-indexing/main.py verify
python day-25-rag-chat/main.py chat
```

Параметры совпадают с актуальной схемой дня 24: `fixed`, candidate K 20, final K 5, inclusive raw cosine ≥0.50, heuristic rewrite, `bge-m3`, `qwen2.5:14b`, strict coverage. Для истории зарезервировано до 4 последних завершённых ходов/2400 символов, для task state — до 6000 символов, context Ollama — 32768 токенов. Число символов не является точным числом токенов модели.

Менять модель генерации можно без пересчёта embeddings; смена embedding-модели требует пересборки индекса. Для менее тяжёлой модели укажите, например, `--answer-model qwen2.5:7b` после её отдельной загрузки; качество разрешения продолжений и coverage нужно проверить заново.

Глобальные параметры ставятся **до** команды:

```bash
python day-25-rag-chat/main.py --answer-model qwen2.5:14b --min-similarity 0.50 chat
python day-25-rag-chat/main.py --history-turns 2 --strategy structural chat
```

Чат проверяет revision выбранного индекса до обращения к модели. Root README входит в общий корпус, поэтому после применения решения индекс нужно пересобрать. `--allow-stale-index` явно разрешает старый индекс, сохраняя его revision в trace. Структура корпуса дня 21 прежняя: root README, README дней 1–20, Python дней 16–20; README дней 21–25 не добавляются в индекс автоматически.

## Диалог, команды и продолжение

На старте чат печатает `session=<ID>`. Обычные вопросы вызывают RAG. Команды управляют диалогом и не считаются вопросами к базе знаний.

```text
/goal Подготовить проверку планировщика дня 18.
/constraint Используем SQLite.
/clarify Речь о расписании дня 18.
/term снимок=сохранённые данные GitHub
Какой процесс выполняет фоновые задания на день 18?
А где это хранится?
/state
/history
/export day-25-rag-chat/reports/check/my-dialogue.json
/quit
```

| Команда | Результат |
|---|---|
| `/new [название]` | Новый изолированный диалог |
| `/use ID`, `/sessions` | Переключение и список диалогов |
| `/state`, `/history` | Полная память задачи; история с источниками и ошибками |
| `/goal TEXT` | Установить или явно изменить цель |
| `/constraint TEXT`, `/clarify TEXT` | Добавить ограничение или уточнение |
| `/term NAME=DEFINITION` | Установить/исправить определение термина |
| `/forget goal` | Очистить цель |
| `/forget constraints KEY` | Удалить конкретное ограничение; KEY виден в `/state` |
| `/forget clarifications KEY`, `/forget terms KEY` | Удалить уточнение/термин |
| `/export PATH.json` | История, ответы, источники, state, trace и события редактирования |
| `/recover` | Пометить pending-ход прерванного процесса как ошибку; применять только после остановки того процесса |
| `/help`, `/quit` | Помощь и выход |

Память также обновляется из обычных сообщений через structured planner. Можно писать «Цель: …», «Ограничение: …», «Уточнение: …», «Термин: … = …» и вопрос в следующей строке. Для свободной формулировки модель предлагает обновления, а приложение требует дословное доказательство из текущего пользовательского сообщения. В state сохраняются значение, evidence, номер хода и происхождение. Цель не заменяется случайным следующим вопросом; существующая цель меняется только по явному указанию. Удаление памяти доступно через `/forget`. Переполнение памяти отклоняет новое обновление с видимым предупреждением, сохраняя старые записи.

Новое уточнение/ограничение добавляется отдельно, даже если planner ошибочно выбрал ключ старой записи. Замена через planner требует явного слова исправления (`исправить`, `заменить`, `вместо`, `теперь` или английского аналога) и указания ключа либо полного прежнего значения в текущем сообщении. Например: `Заменить «Используем SQLite.» на «Используем PostgreSQL.»`. При недостаточно явном указании приложение сохраняет оба утверждения; устаревшее можно удалить через `/forget`. Исправление термина требует его имени в текущем evidence. Повторное подтверждение того же значения не меняет исходное происхождение записи. Корректировка ошибочного ключа видна в `conversation.memory_adjustments`.

```bash
python day-25-rag-chat/main.py chat --session <ID>
python day-25-rag-chat/main.py ask "А какой у него интервал?" --session <ID>
python day-25-rag-chat/main.py sessions
python day-25-rag-chat/main.py state <ID>
python day-25-rag-chat/main.py history <ID>
python day-25-rag-chat/main.py export <ID> --output day-25-rag-chat/reports/check/dialogue.json
```

`ask` без `--session` создаёт новый диалог и печатает его ID. Укажи `--output PATH.json` после `ask`, чтобы сохранить JSON отдельного ответа. Просмотр sessions/state/history/export не требует ни индекса, ни работающего Ollama. После обычного закрытия процесс можно возобновить по ID. Ctrl+C во время запроса сохраняет ход как ошибку, если SQLite доступна; при сбое записи CLI требует проверить историю. Цель первого вопроса не обрезается молча: для запроса длиннее 600 символов задайте краткую цель через `/goal`. Если процесс был принудительно убит, сообщение остаётся pending и доступно через историю; `/recover` позволяет продолжить и отказывает, пока запрос принадлежит живому процессу. Накопившиеся error/pending ходы остаются в полной истории, но не вытесняют последние завершённые ходы из окна planner.

История для planner содержит исходный вопрос, ранее раскрытый `resolved_question` и статус ответа. Отказ по доказательствам не стирает уже раскрытую тему. Для одинакового вопроса подряд приложение повторно использует его принятую формулировку, если значения памяти не менялись. Любой другой вопрос останавливает такое повторное использование; изменение цели, ограничения, уточнения или термина также его отменяет. В trace это видно как `conversation.resolution_reused`. Повторно используется только формулировка: retrieval, выбор цитат и coverage выполняются заново. Эта формулировка не является доказательством фактов или семантической гарантией модели.

## Ответы и источники

Ответы сохраняют extractive-подход дня 24: модель выбирает quote IDs, приложение копирует дословные фрагменты источника. Номера `[1]`, источник, раздел, chunk ID и границы строк назначает приложение. Для фактов текущего ответа используются только новые найденные чанки. История и task state помогают понять цель/термины/ссылки, но не являются доказательствами фактов репозитория.

Это означает, что ответ может быть фрагментом README или кода на языке оригинала, без свободного пересказа/перевода. Память влияет на понимание текущего вопроса и выбор релевантных фрагментов; она не может переписать факты источника или отменить проверки.

Проверка полноты оценивает сведения, запрошенные текущим вопросом. Общая цель диалога не превращает короткий вопрос в запрос полного плана проверки. Для общего вопроса о хранении данных допустим ответ с технологией и именем файла базы; если явно запрошен полный путь, одного имени файла недостаточно. Это инструкция модели о границах вопроса, а не автоматическое одобрение ответа: отрицательный coverage по-прежнему блокирует публикацию в strict-режиме.

Аудитор получает только текущий раскрытый вопрос, требования, происхождение источников и разрешённые proof units из нового ответа. История и task state поступают в planner и селектор, но не в аудит доказательств. Для навигации аудитор также получает до 32 дословных имён/файлов из текстов разрешённых proof units с их ID; индекс не добавляет фактов и не меняет verdict. Названия документов-источников не используются как доказательство имени рабочей базы или пути.

Для Markdown-таблиц добавляется ограниченный индекс строк: дословный заголовок столбца, дословное содержимое ячейки, ID строки и ID заголовка. Заголовок, разделитель и строка должны принадлежать одному claim и быть разрешены текущей proof schema. Так модель видит, что имя из столбца «Сервер» относится к серверу, а имя из столбца «Инструменты» — к инструменту. Индекс не заменяет исходные доказательства и не переопределяет covered. Для простого перечисления селектору предлагается выбирать таблицу/список без лишних описаний полного сценария.

Каждый ответ выводит блок `Источники / Sources`. Если контекст отсутствует, ссылка неоднозначна, модель отказала либо доказательства не прошли проверку, выводится отказ, уточняющий вопрос и явное отсутствие подтверждённых источников. Приложение не придумывает ссылок для отказа. Technical failure сохраняется отдельным статусом `error`, без фиктивного ответа модели.

По умолчанию `--coverage-policy strict`: отрицательная проверка полноты блокирует публикацию. Опциональный `diagnostic` сохраняет правила дня 24: может показать точные фрагменты, но явно помечает отрицательный/неуспешный аудит и требует просмотра источников. Отрицательная оценка не превращается в положительную. В оценке дня 25 такой ход не проходит `coverage_pass`.

## Два длинных сценария

`scenarios.json` содержит **2 × 12 пользовательских вопросов**; вместе с ответами это 48 сообщений. Первый сценарий — планировщик дня 18, второй — полный MCP-флоу дня 20. Есть короткие продолжения, определения терминов, ограничения, уточнения, временный уход на другую тему и возвращение к цели. После шестого хода хранилища закрываются и открываются заново. На поздних ходах исходная цель уже вне окна истории, но остаётся в task state.

Технический стенд:

```bash
python day-25-rag-chat/main.py offline-demo
```

Он использует настоящий корпус, chunking, SQLite cosine search, HTTP-клиент Ollama, строгие валидаторы дня 24 и сохранение диалогов. **Embeddings — lexical hash-256; planner/selector/coverage — scripted HTTP-stand-in.** Для стенда явно заданы 40/20/cosine0.0, а не production-профиль. Проверка успешно прошла на всех 24 ходах, с 48 отдельными embedding/search-вызовами. Это проверка кода и протокола, а не качества BGE-M3/Qwen. `reports/verified/offline.json`, журнал тестов и читабельные диалоги включены в решение.

Настоящий прогон на твоём Ollama:

```bash
python day-25-rag-chat/main.py --answer-model qwen2.5:14b evaluate \
  --output day-25-rag-chat/reports/check/live.json
```

Он использует те же 2 сценария, production-параметры, настоящую модель и новый поиск на каждом ходе. Проверяются: answered, текущий retrieval, точность источников/цитат, ожидаемый документ, сохранённая цель, отсутствие ошибок planner, strict coverage, полная история, все ограничения/уточнения/термины после перезапуска.

Exit 0 — все автоматические проверки прошли; exit 1 — отчёт сохранён, часть проверок не прошла; exit 2 — ошибка конфигурации/запуска. Ошибки отдельных ходов сохраняются в отчёте и историях, оценка продолжается. После прогона нужно заполнить `manual_review` каждого хода: релевантность, полнота, соблюдение цели. Точные цитаты и положительный модельный verdict сами по себе не доказывают качество ответа.

В среде подготовки Python 3.12.14: **181 тест дня 25** прошёл на v24, включая две серии по 12 отдельных процессов, checkpoint/resume и аварийное завершение владельца запроса. **135 проверок дня 24/console** и **34 проверки дней 21–23** заново пройдены. Код дней 21–24 совпадает с опубликованным `8f2b24f`. Реального Ollama здесь нет. Пользовательский живой summary-тест v22 отдельно проверен по источникам и прошёл; точечный scheduler-вопрос v23 также прошёл; теперь также проверен полный пользовательский live v24: 24/24 по ручному ревью. Целевая версия пользователя — Python 3.13; использованные синтаксис и stdlib совместимы.
