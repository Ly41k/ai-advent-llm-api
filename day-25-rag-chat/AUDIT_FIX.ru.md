# Исправление независимого аудита v5

Живой followup-v4.json подтвердил исправление разрешения темы. Вопрос раскрыт как «А где хранятся снимки, которые сохраняет worker на день 18?», память не менялась, warnings пусты, свежий поиск выбрал два README дня 18. Обе попытки selector выбрали q1_3 и q1_10. Quotes/source identity прошли; coverage отказал.

Теперь reason аудитора: «конкретный файл SQLite не указан». Но в его разрешённых proof units есть p2_1: «Данные `schedule.db` сохраняются между перезапусками; файл исключён из Git.». p1_2 прямо говорит о сохранении снимков в SQLite. Аудитор учитывает p1_2 и пропускает имя файла в другом фрагменте. Полный путь этими цитатами действительно не подтверждён, но вопрос полного пути не запрашивает.

## Изменения

ContextProvider разделяет задачи по structured schema:

- planner и селектор используют bounded history и task state для понимания цели/темы;
- аудит proof_ids получает только текущий question_context, coverage_requirement, разрешённые proof units и их lesson provenance;
- история прежних ответов/отказов и task state в запрос аудитора не добавляются;
- индекс дословных inline-code/file-like имён из разрешённых proof units помогает найти конкретное имя и его proof ID;
- индекс ограничен 32 строками, не сканирует lesson_scope.source, историю или память и не добавляет утверждений об этих именах;
- модель должна проверить ВСЕ разрешённые фрагменты, в том числе разных claims, и дать собственный verdict.

Никакое covered=false не превращается кодом в true. Неизвестные/неподходящие proof IDs, неподтверждённые цитаты, отсутствие запрошенных данных по-прежнему ведут к отказу. Порог, параметры поиска, рабочие базы и Python-модули дней 21–24 не изменены.

## Проверка

43 теста дня 25 прошли, включая два технических сценария по 12 ходов. Новые проверки подтверждают:

- отсутствие истории/цели в запросе аудитора и сохранение отрицательного ответа провайдера;
- индексирование только schema-allowed proof text, исключение имени документа и неподходящего proof ID;
- сохранение памяти/истории в запросе селектора;
- ограничение размера индекса и безопасную обработку некорректного входа.

Существующие тесты строгого отказа, точных цитат, неверных IDs, перезапуска и сохранения цели также прошли. На настоящем наборе proof units из followup-v4.json построен индекс schedule.db → p2_1; результат приложен в reports/verified/audit-trace-replay.json. Это проверка формирования входа, не доказательство качества настоящего Qwen. Живой ответ после v5 нужно проверить отдельно.

## Применение

Архив включает изменения v1–v4, применяется поверх исходного решения или любого предыдущего патча. Из корня репозитория:

```bash
unzip -o ~/Downloads/day-25-audit-fix-v5.zip
python day-25-rag-chat/test_day25.py -v
```

Ожидается Ran 43 tests и OK. Повторить исходный короткий вопрос в прежней сессии:

```bash
python day-25-rag-chat/main.py ask \
"А где это хранится?" \
--session 2cb61350c3d54c218d260e6a5cd65969 \
--output day-25-rag-chat/reports/check/followup-v5.json
```

Миграция chats.db, пересборка knowledge.db и восстановление памяти не нужны. Поиск и строгий audit выполняются заново; предыдущий отказ остаётся в истории. При новом отказе анализировать raw ответа аудитора и выбранные proof units в followup-v5.json. Не объявлять проверку пройденной только на основании локальных scripted тестов.
