# v14 — Полные таблицы и связь вводного абзаца с продолжением

## Подтверждённые проблемы

В `long-detour-v13.json` фоновые задания дня 18 правильно отнесены к `worker.py`, память задачи дня 20 сохранена, но в ответ попала лишняя таблица. Её последняя строка `| Работает` обрезана границей fixed chunk; дословность такой цитаты не делает её полной.

В `long-return-v13.json` явный возврат к цели без указания дня правильно восстановил день 20. Registry описан верно, но длинный выбранный абзац заканчивается «При успешном запросе путь следующий:», а refiner удалил следующий фрагмент с цепочкой. Guard v9 проверял только вводные строки длиной до 300 символов.

Оригиналы и отдельные reviews сохранены в `reports/live/`. Основные функции переключения/возврата прошли; дефекты оформления не скрыты положительным coverage.

## Исправление

Перед selector распознанные pipe-таблицы проверяются по числу столбцов: заголовок, separator и строки. Если строка имеет другую ширину, весь quote ID исключается из DATA и enum schema. Остальные source quotes, question, requirements и feedback сохраняются. Поддерживаются экранированные `\|`, пустые ячейки и необязательный завершающий delimiter. Это проверка формы таблицы, а не истинности фактов. Неопознанный текст не считается таблицей по догадке. Источник и индекс не переписываются, неполная таблица не достраивается и не обрезается до удобного ответа.

Локальный guard запрещает исключённые ID, даже если модель вернула их вопреки schema. Исключения с исходным текстом и причиной сохраняются в `validation.fragment_filters`.

Связь прозы, заканчивающейся двоеточием, со следующим fenced-фрагментом того же chunk применяется ко всем допустимым абзацам до 1600 символов. Guard проверяет все пары ID; ограничение 16 пар/8000 символов относится только к навигационной подсказке. Refiner также получает буквальные пары ID. Если вводный абзац выбран, его продолжение должно идти сразу после него. Иначе кандидат отвергается; приложение не переписывает абзац и не подставляет код автоматически.

После отбора действует прежний независимый strict coverage audit по всему вопросу. Недостаток доказательств по-прежнему приводит к отказу. Дополнительных попыток сверх прежних двух нет. Модельные инструкции и guards не гарантируют минимальную длину каждого будущего ответа; полные соседние фрагменты иногда необходимы для сохранения исходного контекста.

Python дней 21–24, порог поиска, базы и история не меняются. Индекс пересобирать не нужно. Архив содержит все исправления v1–v14; пользовательские базы и `.env` исключены.

## Проверки

95 автоматических тестов PASS, включая реальные тексты README, фильтр неполной таблицы без редактирования других цитат, запрет excluded ID, сохранение полных таблиц/пустых ячеек/escaped pipes, long intro в initial selector/refiner, обязательность поздних пар за пределами навигационного бюджета, отрицательные coverage/forged-ID/token-limit проверки и 2×12 scripted сценария. Scripted model отдельно соблюдает зависимости intro/code; его поведение не выдаётся за успешный live Qwen.

Реальный `long-vps-v13.json` пройден: один точный абзац явно подтверждает, что VPS и worker не нужны, proof p1_5 содержит это предложение, память не изменена. Чистые новые live-сценарии 12+12 пока не пройдены.

## Установка и следующий шаг

Распакуйте архив в корень `ai-advent-llm-api` с заменой `day-25-rag-chat/`.

```bash
python day-25-rag-chat/main.py ask \
"Для сравнения: какой процесс дня 18 выполняет фоновые задачи?" \
--session 4fb98ce5a966406688e4d80b51cfa7ba \
--output day-25-rag-chat/reports/check/long-detour-v14.json
```

Ожидается worker.py с актуальным источником дня 18 и неизменной целью дня 20. Оборванная таблица не должна быть опубликована. Затем отдельно повторяется возврат к цели, чтобы проверить связь длинного абзаца с продолжением настоящим Qwen.
