# Исправление follow-up v3

В живом followup.json вопрос «А где это хранится?» правильно разрешён как «А где хранятся снимки, которые сохраняет worker на день 18?». После старта нового процесса сохранились цель, два ограничения, оба уточнения и термин. Поиск выполнен заново: 20 кандидатов, два чанка после порога 0.50 — README дня 18 на русском и английском.

Обе попытки выбора цитат вернули q1_3 (сохранение снимков в SQLite) и q1_10 (данные schedule.db сохраняются между перезапусками). Coverage вернул covered=false: конкретный путь к SQLite не указан. Общий вопрос не запрашивал полный путь, поэтому такой отказ считаем требованием избыточной детализации. Само имя schedule.db доказано источником, а полный путь из этих двух цитат не доказан. Порог и строгие проверки не менялись.

Также planner предложил дописать разрешённый вопрос к прошлому уточнению и использовать evidence из прошлого сообщения. Проверка текущего evidence отклонила это предложение, поэтому память не повреждена; предупреждение полезно для диагностики.

## Что изменено

В conversation.py добавлены инструкции:

- обычный вопрос-продолжение разрешается без обновления task state (updates=[]);
- нельзя дописывать разрешённый вопрос к значению памяти или копировать evidence из истории;
- полнота оценивается по текущему вопросу, а не по всей сохранённой цели;
- общий вопрос о хранении допускает доказанное название технологии и файла; полный путь, настройки размещения и команды требуются при явном запросе этих деталей;
- запрос полного пути не удовлетворяется одним именем файла, путь нельзя вывести из имени документа-источника;
- предпочтительны минимальные полные цитаты по текущему вопросу.

Приложение не переписывает отрицательный verdict в положительный. covered=false по-прежнему ведёт к отказу. Модули дней 21–24, retrieval, порог 0.50, exact evidence и strict policy не изменены. Это изменение промптов, которое требует повторной проверки настоящего Qwen.

## Локальная проверка

Прошли 37 тестов дня 25, в том числе два технических сценария по 12 ходов. Новый тест воспроизводит точный planner JSON из followup.json и проверяет сохранение памяти, отклонение исторического evidence, разрешение темы и новый поиск. Выбор доказательств в нём выполняется scripted HTTP-стендом, поэтому он НЕ доказывает исправление качества Qwen. Второй новый тест воспроизводит отрицательное coverage и подтверждает, что scope-инструкция не обходит отказ и строгую политику.

## Применение

Архив включает изменения v1 и v2; его можно применять к исходному решению или поверх предыдущих патчей. Распаковать из корня репозитория. Рабочие базы и история не входят в архив, пересборка knowledge.db не нужна.

```bash
unzip -o ~/Downloads/day-25-followup-fix-v3.zip
python day-25-rag-chat/test_day25.py -v
```

Ожидается Ran 37 tests и OK. Повторить ровно тот же вопрос в прежней сессии:

```bash
python day-25-rag-chat/main.py ask \
"А где это хранится?" \
--session 2cb61350c3d54c218d260e6a5cd65969 \
--output day-25-rag-chat/reports/check/followup-v3.json
```

Ожидаем разрешение темы снимков дня 18, новый поиск, ответ с подтверждёнными источниками о SQLite/schedule.db и сохранение всей памяти. Если настоящий Qwen всё ещё откажет или предложит недопустимое обновление памяти, анализировать followup-v3.json; успешная локальная проверка не является гарантией положительного live verdict.
