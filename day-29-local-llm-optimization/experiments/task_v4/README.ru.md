# V4: отдельный шаблон для вопросов о проверке

## Результат контрольного V3

`control-v3.json` завершён: 30 наблюдений, 6 переиспользованы, 24 новых ответа.
Baseline прошёл 15/15 эвристических проверок; V3 — 12/15. Это не оценки
семантической привязки цитат: в baseline остаются повторы и ошибки grounding.

V3 правильно ответил на вопросы о GitHub-инструменте, worker, трёх инструментах
композиции и отказался придумывать выручку. Но на русском вопросе о проверке VPS
все три раза дал только «Проверяйте journalctl и запрашивайте свежую сводку через
агента». Утверждение подтверждено цитатой, но процедура неполна: пропущена
проверка состояния службы. Не достаточно просто вставить слово systemctl:
нужны осмысленные проверки и объяснение того, что они устанавливают.

Общая медиана V3 6.09 с против 26.67 с baseline скрывает дорогой prefill при
смене вопросов. Например, медианы трёх ответов на GitHub-инструмент составили
45.62 и 56.28 с, на три инструмента композиции — 45.33 и 57.24 с. Скорость
следует оценивать по вопросам и с учётом prompt cache; сравнение не доказывает
одинаковое ускорение каждого запроса. Сокращать процедуру до неполного ответа
ради времени нельзя. V3 пока не проходит полный контрольный набор.

## Изменение

Короткий фактический шаблон V3 сохраняется побайтно. Для вопросов с формой
«как ... проверить» / «how ... verify/check/test/confirm/prove» используется
отдельный шаблон: дать конкретные документированные проверки, различать
работу процесса и повторное выполнение заданий, сохранять команды и объяснять
назначение проверок. Пример про вымышленные резервные копии показывает два
claim с разными доказательствами. В шаблоне нет ожидаемого ответа Day 18,
systemctl, journalctl, номера кейса или реального ожидаемого quote_id.

Выбор шаблона выполняется локальным правилом по тексту вопроса, без обращения
к модели. Рубрика, expected_terms и expected_sources в правило не передаются.
Это настройка prompt под два типа задач. Retrieval, источники, модель,
параметры, schema JSON, seeds и измерение ресурсов не меняются. Правило
покрывает указанные формы вопросов, не все возможные способы задать процедуру.

Профиль сохраняет имя `focused-v3-q4`: переименование само по себе заставило
бы пересчитать старые ответы. Реальные сообщения и их SHA-256 уже входят
в ключ эксперимента. Поэтому изменённая процедура получает новые ответы,
а фактические вопросы с прежними сообщениями используют прежние ответы.
В JSON сохраняются фактически отправленные сообщения для каждого вопроса.
Baseline использует исходный шаблон для всех вопросов.

## Установка и запуск

Нужно установленное дополнение V3. Распакуйте архив в корень репозитория;
он добавляет только `experiments/task_v4/`. Исходные файлы и кэш не заменяются.

```bash
python day-29-local-llm-optimization/experiments/task_v4/main.py run \
  --profiles baseline focused-v3-q4 \
  --split all \
  --case base-07 base-06 base-08 base-10 negative-03 \
  --repeats 3 \
  --retry-from day-29-local-llm-optimization/reports/check/control-v3.json \
  --output day-29-local-llm-optimization/reports/check/control-v4.json
```

При прежнем окружении 27 наблюдений переиспользуются, три новых ответа
выполняются только для оптимизированного вопроса про VPS (`base-10`).
Проверка вместимости prompt и прогрев учитываются отдельно. Повтор после
трёх ответов не вызывает новых генераций. Не меняйте индекс, модели, исходные
файлы V1, series и параметры; при другом пути отчёта исправьте `--retry-from`.
Для оценки до генерации можно заменить `run` на `plan`.

```bash
python day-29-local-llm-optimization/experiments/task_v4/main.py verify \
  day-29-local-llm-optimization/reports/check/control-v4.json
```

Дальше проверяются все три новых ответа вручную: есть ли проверка службы,
документированные команды для журналов, проверка реальных повторных запусков
или свежих результатов, поддерживает ли выбранная цитата каждый факт.
Источники могут ограничить полноту процедуры; нельзя приписывать им отсутствующие
наблюдения или выдавать настройку службы за доказанный успешный запуск.
Успех V4 на реальной Qwen пока не измерен.

## Проверки без локальной модели

```bash
python -m unittest discover \
  -s day-29-local-llm-optimization/experiments/task_v4 -p 'test_task_v4.py' -v
```

Тесты проверяют неизменность фактических prompt и baseline, изменение только
процедурного prompt, импорт старых результатов и выполнение только недостающих
трёх ответов на фиктивном локальном транспорте. Они не оценивают реальный ответ Qwen.
