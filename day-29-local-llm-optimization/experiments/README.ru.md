# Уточнение prompt после ручной проверки

Это дополнение к V1. Распакуйте папку `day-29-local-llm-optimization/` из архива
в корень существующего репозитория. Дополнение добавляет только `experiments/`;
исходные Python-файлы V1, старые профили, отчёты и кэш не заменяются.

## Что обнаружено

В `baseline-worker-v1.json` все три ответа правильно называли `worker.py`,
но добавляли инструкции по VPS и ссылались на `e2-q6` для утверждения о
`GITHUB_TOKEN` и Groq, которое подтверждается `e2-q5`.

В `worker-pair-v1.json` baseline был переиспользован три раза. Все три новых
ответа `candidate-q4` убрали утверждение о ключах, но всё ещё добавляли инструкции
по запуску и VPS. Фраза «ensure 24/7 operation» также сильнее, чем инструкция по
настройке службы: инструкция сама по себе не гарантирует бесперебойную работу.

Проверка JSON, существования ID и наличия слова `worker` пропустила эти недостатки.
Поэтому её PASS не считается подтверждением качества. Старые ответы сохраняются
как результат измерения, без исправления их текста или ссылок задним числом.

## Что изменено

Новый шаблон требует отвечать только на запрошенное, оставлять ненужные слоты
`null`, не дополнять простой вопрос инструкциями по развёртыванию и проверять
каждый факт по тексту именно выбранного `quote_id`. В шаблоне нет правильного
ответа, имени `worker.py`, номера вопроса или ожидаемого ID цитаты.

`focused-q4` сохраняет модель, temperature, max_tokens и num_ctx профиля
`candidate-q4`; меняется только текст prompt. `focused-q5` — тот же шаблон с Q5.
`prompt-focused` позволяет отдельно сравнить новый шаблон с baseline при его
исходных параметрах. Пока запускать дополнительные профили не требуется.

Запуск через `focused_v2.py` подставляет новый шаблон в существующий механизм
compact. Поэтому поле `prompt` остаётся `compact`, а имя профиля и SHA-256 реальных
сообщений отличают новый эксперимент. Механизм генерации, измерений, seeds,
retrieval и формат отчёта остаются V1. Не запускайте новые профили через обычный
`main.py`: он использует исходный compact-шаблон.

## Следующий запуск: три ответа нового профиля

Из корня репозитория, с запущенной Ollama и активной `.venv`:

```bash
python day-29-local-llm-optimization/experiments/focused_v2.py run \
  --profiles baseline focused-q4 --case base-07 --repeats 3 \
  --retry-from day-29-local-llm-optimization/reports/check/worker-pair-v1.json \
  --output day-29-local-llm-optimization/reports/check/worker-focused-v2.json
```

При неизменных исходных файлах V1, модели, индексе, оборудовании и параметрах
baseline берётся из кэша или указанного отчёта: три новых ответа выполняются
только для `focused-q4`. Ответы `candidate-q4` сохраняются в прежнем отчёте и
не запрашиваются. Повтор той же команды переиспользует и три ответа `focused-q4`.
Проверка вместимости prompt и прогрев отдельно учитываются как maintenance calls.

Если путь старого отчёта другой, замените значение `--retry-from`. Не меняйте
`--series` или исходные файлы V1 между этими запусками. Для предварительной оценки
можно заменить `run` на `plan` в этой команде. `plan` не обращается к модели;
точное совпадение текущего окружения проверяется при `run`.

Для проверки нового отчёта:

```bash
python day-29-local-llm-optimization/experiments/focused_v2.py verify \
  day-29-local-llm-optimization/reports/check/worker-focused-v2.json
```

После запуска проверьте все три ответа вручную: назван ли нужный процесс,
отсутствуют ли лишние инструкции, подтверждается ли каждый факт указанной
цитатой. Сравнение `candidate-q4` и `focused-q4` по двум сохранённым отчётам
покажет эффект изменения только шаблона. Исправление поведения модели пока
не измерено: новый prompt требует проверки на реальной локальной модели.

## Проверка дополнения без модели

```bash
python -m unittest discover \
  -s day-29-local-llm-optimization/experiments -p 'test_focused_v2.py' -v
```

Тесты используют фиктивный локальный транспорт. Они проверяют сохранение
baseline, независимость нового prompt и отсутствие повторных генераций после
трёх ответов. Они не оценивают смысл реального ответа Qwen.
