# V6 — процедурное качество без скрытого переписывания ответов

## Причина продолжения работы

V5 получил 15/15 по лексической рубрике, но три одинаковых VPS-ответа содержат
неподтверждённый claim: `systemctl status bublik-day18` привязан к `e1-q6`,
где нет этой команды. Кроме того, статус процесса не доказывает выполнение
работы. Ответ не описывает проверку появления повторных результатов.
Такое качество не считаем закрытым только потому, что задание можно сдать.

## Изменения

1. Отдельная подготовка доказательств для процедурных вопросов: явные номера
   дней ограничивают проекты, общие чек-листы исключаются при наличии другой
   информации, локальные тесты не подменяют проверку VPS, инструкции запуска
   отделены от наблюдений. Детальные таблицы процедуры остаются. Источники на
   языке вопроса идут первыми; переводы не считаются гарантированно одинаковыми
   и не удаляются только из-за языка. Каждый отбор/отсев записан. При пустом
   результате фокуса остаётся исходный каталог. Новых фактов не добавляется.
2. Шаблон разделяет состояние процесса, результат выполнения и периодичность.
   Каждый пункт требует поддержки собственной цитатой. План наблюдения не
   выдаётся за фактически пройденную проверку. Для других процедур используются
   относящиеся к ним действия, без обязательного выдуманного system status.
3. Независимый guard проверяет технические фрагменты именно выбранной цитатой,
   распознаёт некоторые ошибочные выводы из status и пропуски периодической
   процедуры. Команды, filenames, tool names и аргументы проверяются строго.
   Источником имён executable служат реальные shell-блоки каталога.
4. Отдельный JSON/Markdown-аудит хранит диагноз, ключ опыта и hash сырого ответа.
   Он не меняет generation.answer/response/quality и не подставляет более удобные
   IDs. Оригинальный отчёт продолжает проверяться исходным verify/import.

## Границы автоматической проверки

`blocked` означает выявленный дефект или неполноту. `ready_for_manual_review`
означает только отсутствие выявленных дефектов. `semantically_verified=false`
и `automatic_publication_allowed=false` сохраняются в обоих случаях.
Лексические признаки не доказывают весь смысл предложения. Строгая проверка
буквальных фрагментов может потребовать ручного разбора допустимой переформулировки.
Guard не является ещё одной LLM и не делает модельных вызовов.

V6 ещё не прогонялся живой Qwen в среде подготовки архива. Включённая оценка
V5 — повторный разбор прежних живых измерений, а не новые ответы V6.

## Первый контроль на Mac

```bash
python day-29-local-llm-optimization/experiments/quality_v6/main.py run \
  --profiles baseline focused-v3-q4 \
  --split all --case base-06 base-07 base-08 base-10 negative-03 --repeats 3 \
  --retry-from day-29-local-llm-optimization/reports/check/control-v5.json \
  --max-new-observations 3 \
  --output day-29-local-llm-optimization/reports/check/control-v6.json
```

Ожидается 27 reused / 3 new при прежнем окружении. Исходные baseline и
справочные messages не меняются. Хеш policy включён в новый процедурный prompt;
изменения policy требуют новых процедурных наблюдений. Hash guard отдельно
записан в аудите: изменение оценки не требует снова получать тот же ответ.

Профиль называется `focused-v3-q4` ради прежних ключей. Называть его V3-процедурой
по одному имени нельзя: нужно смотреть реальные messages/prompt_sha256.

Лимит 3 новых наблюдений ограничивает стоимость даже при изменённой среде;
такой запуск может остановиться как paused. За максимум три ответа на один
неизменённый опыт отвечает ограничение repeats и кеш. Плохой, но законченный
ответ не повторяется. Служебные probe/warmup считаются отдельно.

Отправить на разбор нужно `control-v6.json` и `control-v6.quality.json`.
Если quality exit code 1, файлы всё равно сохранены. Не удаляй кеш и не меняй
series для обхода результата. Повтор команды полезен только для действительно
незавершённых слотов, а не для получения нового варианта законченного ответа.

## Offline-разбор любого сохранённого V1–V6 отчёта

```bash
python day-29-local-llm-optimization/experiments/quality_v6/main.py audit \
  day-29-local-llm-optimization/reports/check/control-v5.json
```

Ноль HTTP-вызовов и генераций. Создаётся отдельный `control-v5.quality.json`
и Markdown. Exit code 1 здесь ожидаем: известные дефекты V5 обнаружены.
Эта команда не меняет индекс, исходные отчёты или кеш наблюдений.

## Проверка переноса подхода после первого ручного ревью

Сначала замораживаем V6 после оценки VPS-ответов. Затем используются две новые
формулировки из `experiments/quality_v6/questions-transfer.json`: английская
проверка периодического worker и русская проверка отчёта Day 20. По ним ещё
не получено ответов. Это небольшой transfer-контроль, не доказательство
универсального качества. Каждый вопрос запускается отдельным пакетом по 3:

```bash
python day-29-local-llm-optimization/experiments/quality_v6/main.py run \
  --profiles focused-v3-q4 --split evaluation \
  --questions day-29-local-llm-optimization/experiments/quality_v6/questions-transfer.json \
  --case quality-transfer-01 --repeats 3 --max-new-observations 3 \
  --output day-29-local-llm-optimization/reports/check/quality-transfer-01-v6.json
```

Для второго заменить ID/filename на quality-transfer-02. Пока не нужно запускать
оба пакета: сперва разбираем первый контроль. Если по transfer-вопросу меняем
prompt, он становится материалом настройки; для независимой оценки нужен
новый отложенный вопрос. Старые слабые ответы остаются в истории.
