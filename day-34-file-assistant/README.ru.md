# День 34 — AI File Assistant

**Course Minimum: PASS после независимой редакционной проверки.** Техническая приёмка и качество Usage — PASS. Исходный модельный ADR остаётся **PARTIAL**, отдельный редакционный ADR — PASS. Исторические автоматические `full_e2e: NOT_ACCEPTED` не изменены. См. [итоговый отчёт](FINAL_REPORT.ru.md) и [публичную приёмку](evidence/acceptance.json).

## Задание и границы

Создать ассистента, который читает файлы проекта, ищет в нескольких файлах, анализирует содержимое, создаёт или меняет файлы и сам инициирует эти операции по цели пользователя. Минимум два сценария, работа с 2–3 файлами, сохранённые изменения или diff и повторное воспроизведение.

Минимум реализован на стандартной библиотеке Python: локальные файловые инструменты и ограниченный модельный цикл. Ассистент создаёт Markdown, не меняя предыдущие задания. Это учебный модуль на закреплённых исходниках, без новой RAG-системы и сложной системы агентов; он не позиционируется как универсальный production-агент. MCP для инструментов Day 34 не нужен; реализация MCP Day 33 служит предметом анализа.

## Архитектура и инструменты

`main.py` — CLI. `agent.py` передаёт цель и недоверенные результаты инструментов адаптеру, проверяет каждое выбранное действие и исполняет его через `file_tools.py`. В `llm_adapter.py` находятся Groq, явно сценарные offline-fixtures и replay сохранённых решений. `openai_adapter.py` реализует strict native function calling через curl. `resume.py` и `quote_repair.py` сохраняют историю отдельно согласованных продолжений после локальных отказов.

| Инструмент | Действие |
|---|---|
| `list_files` | Список разрешённых путей, число строк и SHA-256 |
| `search_files` | Буквальный поиск по выбранным или всем разрешённым файлам, пути и номера строк |
| `read_file` | Файл или диапазон, максимум 200 строк за операцию, явная пагинация/EOF |
| `write_file` | Эксклюзивное создание Markdown по basename в новой папке Day 34; проверка точных source evidence |

Настоящая модель выбирает инструменты, аргументы, поисковые выражения, диапазоны чтения, имя/содержимое документа и завершение. Python проверяет контракт и границы, но не задаёт последовательность live-действий. OpenAI использует строгие native schemas, Groq — строгий JSON-контракт решений. Offline-fixtures заранее написаны и **не доказывают самостоятельность настоящей LLM**.

## Исходники и безопасность

`inputs.json` закрепляет 17 Python/JSON-файлов Day 33 на `25ba00685d0748ebe533570711b75e0d187ab20b`. Оба сценария читают `main.py`, `mcp_client.py` и `support_agent.py`; дополнительные файлы выбирает модель.

- Чтение по allowlist с проверкой SHA; произвольное чтение проекта запрещено.
- Запись только в `day-34-file-assistant/results/<новый-run-id>/`; эксклюзивное создание без случайной перезаписи.
- Запрет абсолютных путей, traversal и symlink escape через directory descriptors и `O_NOFOLLOW`.
- Исходник до 65 536 байт, документ до 20 000 байт, максимум 24 файловые операции и ограниченное число модельных шагов.
- Текст файлов — недоверенные данные, не инструкции агенту. Shell-команды от LLM не выполняются.
- Evidence ссылается на уже прочитанные строки и совпадает с ними дословно. Это проверяет происхождение цитат, но не каждое смысловое утверждение.
- Явное разрешение провайдера, неизменяемые резервы POST, лимиты токенов/стоимости, отсутствие автоматических retry/fallback. Новые облачные вызовы в поставку не входят.

## API и история ошибок

Groq `openai/gpt-oss-120b`: всего 4 POST. Сохранены отказы `tool_use_failed`, неверная схема пустого объекта и поздний `json_validate_failed`, причина которого не установлена. Успешный ответ самостоятельно выбрал `list_files`. Слепые повторы не засчитывались как приёмка.

OpenAI `gpt-5.4-mini`: всего 10 POST, все HTTP 200, по пять на сценарий с учётом продолжений. Локальные остановки: `invalid_line_range` при запросе более 200 строк и позже за EOF, затем `quote_mismatch`. Ограниченное чтение и явное продолжение сохранённого состояния сохранили исходные аргументы; EXACT-проверка цитат не ослаблялась. Каждое продолжение согласовывалось отдельно. Неудачные попытки и receipts остаются приватными и неизменными.

Сохранённый usage: **83 631 input + 5666 output = 89 297 токенов**, включая 21 248 reported cached input. Консервативная оценка **$0.08822025**, с учётом cache — **$0.07387785**; фактический billing неизвестен. Общий резерв $0.44085975 при потолке $0.50. Полный Groq usage неизвестен; сохранённый успешный ответ содержит 1140 токенов. См. [суммы](evidence/api-usage.json) и [сводку POST OpenAI](evidence/openai-posts.json). Финализация — **ноль новых POST**.

## Установка и проверка на Mac

Из корня репозитория с Python 3.13; этому модулю не нужны pip-зависимости, ключи, сеть или Ollama для проверки:

```bash
python3.13 -m venv .venv
source .venv/bin/activate
python3.13 day-34-file-assistant/verify_delivery.py
```

Если venv уже активен, достаточно последней команды. В финальном JSON ожидаются `status: PASS`, `offline_tests: 65/65 PASS`, оба replay с `equal: true`, `new_provider_posts: 0`. Исходный Mac v7 65/65 сохранён отдельно. Проверяется поставка и воспроизведение принятой редакционной проверки; новая live/смысловая оценка не выполняется.

Verifier проверяет manifest публикации, 17 входных SHA, неизменность документов/evidence, точный редакционный diff, source evidence, суммы usage, шаблоны приватных данных, состав Git index при его наличии, 65 существующих тестов и оба replay в temporary directory. Приватные локальные результаты остаются на месте. Изменённые tracked/staged файлы должны входить только в состав поставки; лишние файлы вызывают отказ.

Другие реальные offline-команды CLI:

```bash
python3.13 day-34-file-assistant/main.py --help
python3.13 day-34-file-assistant/main.py offline-check --run-id manual-offline-01
```

Для каждого `offline-check` нужен новый run ID, результаты не перезаписываются. Его автоматический `NOT_ACCEPTED` относится к новой live/смысловой приёмке, а не к отдельному принятому финальному review. Verifier воспроизводит публичные проекции через существующие `ReplayAdapter` и агентный цикл. На Mac с сохранёнными приватными traces работает и обычный CLI:

```bash
python3.13 day-34-file-assistant/main.py replay --trace day-34-file-assistant/results/mac-openai-usage-01-resume-01/trace.json --run-id manual-usage-replay-01
python3.13 day-34-file-assistant/main.py replay --trace day-34-file-assistant/results/mac-openai-adr-01-repair-01/trace.json --run-id manual-adr-replay-01
```

Последние две команды требуют исторических локальных результатов и новых output ID. Для публичного verifier они не нужны. Live/resume/repair запускать не следует: разрешённый бюджет генераций исчерпан.

## Публичный состав и ограничения

`evidence/`: исходники двух документов, отдельная редакционная версия, исходные diff/manifests создания, неизменённая автоматическая приёмка, Mac offline-отчёт, API-сводки и две проекции traces с решениями. Сохранены точные canonical requests, аргументы модели, результаты инструментов и SHA документов; raw provider wire, IDs и приватные receipts исключены. Native wire/receipts были проверены до публикации. Публичный replay проверяет сохранённые решения и файловые результаты, не идентичность провайдера или новую генерацию.

`delivery-manifest.json` перечисляет публичные файлы и SHA-256. Приватные `results/`, receipts, сырые HTTP payload, venv и caches исключены. См. [публикацию](PUBLICATION.ru.md), [сценарий видео](CONSOLE_VIDEO.ru.md) и [итоговый отчёт](FINAL_REPORT.ru.md).

Ограничения: буквальный поиск, фиксированные исходники, только создание Markdown, лимиты контекста/операций, POSIX/macOS и ручная смысловая проверка. Post-course backlog: переносимость схем провайдеров, подсказки диапазонов, общая проверка утверждений, расширение входов. Для Day 34 это не требуется. Изменения корневых README могут потребовать перестроения старых RAG-индексов при будущем использовании; сейчас индексы не перестраиваются.
