# День 9 — управление контекстом: сжатие истории

Девятое задание сохраняет последние сообщения без изменений, а старую часть диалога заменяет отдельно сохранённым накопительным summary.

## Мир симуляции

Бублик работает внутри вымышленной исследовательской симуляции из 100 звёздных систем. В каждой системе находится от 4 до 16 планет, а у некоторых планет есть естественные спутники. Если капитан не указал отдельные параметры, Бублик самостоятельно вводит правдоподобные допущения и продолжает исследование. Уточняющий вопрос задаётся только тогда, когда без решения капитана невозможно продолжить или выбор принципиально меняет результат.

## Задание

- хранить последние N сообщений как есть;
- сжимать старые сообщения партиями;
- хранить summary отдельно и использовать вместо полной истории;
- сравнить качество и расход токенов без сжатия и со сжатием.

## Результат

Полная успешная история по-прежнему остаётся в SQLite и не удаляется. В модель отправляется:

```text
system prompt + накопительный summary + несжатые сообщения + текущий запрос
```

Последние 10 сообщений всегда защищены. Пока формируется следующая полная партия, до 9 дополнительных старых сообщений временно остаются в исходном виде. Когда перед защищённым окном накапливается партия из 10 сообщений, `HistoryCompressor` отправляет её вместе с предыдущим summary модели GPT-OSS 20B. Новый накопительный summary заменяет предыдущий в таблице `conversation_summaries`, а `summarized_through_message_id` перемещается вперёд.

## Структура

```text
day-09-context-compression/
├── agent.py
├── compression.py
├── experiment.py
├── main.py
├── memory.py
├── tokens.py
├── README.md
└── README.ru.md
```

- `compression.py` выбирает старые партии и обновляет summary;
- `memory.py` хранит полные сообщения, позицию summary и отдельную стоимость;
- `agent.py` формирует сжатый и полный контексты;
- `main.py` предоставляет интерактивного агента и команды сравнения;
- `experiment.py` воспроизводимо измеряет экономию без обращения к API.

## Хранение

Таблица `conversation_summaries` содержит один накопительный summary для каждого `conversation_id`:

- текст summary;
- ID последнего сжатого сообщения;
- количество исходных сообщений и обновлений;
- накопленные prompt, completion и total tokens, а также стоимость summary.

Полная таблица `messages` сохраняется для диагностики, команды `/history` и честного сравнения со сжатым контекстом.

## Запуск

```bash
pip install -r requirements.txt
python day-09-context-compression/main.py
```

Команды:

- `/history` — последние записи полной истории;
- `/summary` — сохранённый summary и стоимость его создания;
- `/compare` — один вопрос с полной и сжатой историей;
- `/stats` — стоимость основных запросов вместе с расходами на summary;
- `/dialogs` — переключение диалога;
- `/exit` или `выход` — завершение.

Локальное сравнение токенов:

```bash
python day-09-context-compression/experiment.py
```

Эксперимент сравнивает короткую, среднюю и длинную синтетические истории без обращения к Groq.

## Сравнение качества

Используйте диалог минимум с 20 завершёнными сообщениями, чтобы появился summary. Выполните `/compare` и задайте вопрос, зависящий от ранних фактов и последних решений. Команда дважды отправит один вопрос с одинаковыми настройками модели:

1. со всей успешной историей;
2. с накопительным summary и последними 10 сообщениями.

Сравните, сохранили ли оба ответа факты, решения капитана, числовые значения и открытые вопросы. Команда также показывает фактические prompt tokens и стоимость обоих ответов. Запросы сравнения не добавляются в историю.

## Честный расчёт стоимости

Создание summary является дополнительным API-вызовом. Его токены и стоимость сохраняются отдельно и учитываются командой `/stats`. Компрессия становится выгодной, когда экономия входных токенов на последующих запросах превышает разовую стоимость обновления summary.

## Текущие ограничения

- качество summary зависит от модели;
- качество двух ответов сравнивается вручную, без третьей Judge-модели;
- используются фиксированные значения: 10 последних сообщений и партия из 10 сообщений;
- локальный подсчёт является оценкой, для биллинга приоритетны данные Groq;
- режим сравнения выполняет два оплачиваемых API-вызова.

## Итог девятого дня

Бублик сохраняет недавние детали, сжимает старый контекст без удаления исходной истории, учитывает реальную стоимость компрессии и показывает компромисс между качеством и расходом токенов.
