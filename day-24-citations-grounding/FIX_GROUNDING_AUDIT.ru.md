# Идентификатор файла и полнота ответа — 2026-10-03

## Что показал worker_verified.json

Ответ уже называет `worker.py`, но публикуется отказ (`evidence_validation_failed`). Обе попытки одинаковы. Retrieval нашёл правильные документы; cosine первого README равен 0.59395 при пороге 0.50.

Draft выбирает `q1_3` и `q3_3`. В них есть описание независимого worker и сохранения снимков, но **нет имени worker.py**. Строка Components, прямо называющая файл и его работу, уже находится в каталоге (`q1_7` или `q3_6`), однако не процитирована. Поэтому одних flags quotes_exact/sources_valid недостаточно: они подтверждают дословность и происхождение, а не каждую деталь ответа.

Verifier ставит supported=true и пишет, что имя файла содержится в выбранных цитатах. Это ошибка. Одновременно он ставит answers_question=false, не указывая, какой части вопроса не хватает в ответе. Первая проблема — неподтверждённый конкретный идентификатор; вторая — непрозрачный отказ по полноте. Просто заменить false на true было бы неверно.

## Что изменено

1. **Локальная проверка Python-файлов.** Имя вида `worker.py` в утверждении должно буквально присутствовать в его цитатах или пути цитируемого источника. Общая фраза про worker в README не проходит. Это ограниченная проверка имени, не доказательство поведения. Семантический verifier остаётся обязательным.
2. **Выбор подходящих фрагментов.** Каталог для генератора перечисляет python_files каждого фрагмента. При ошибке repair получает существующие ID, содержащие названный файл. Приложение не добавляет цитату само и не использует эталонный ответ.
3. **Обоснование полноты.** Verifier возвращает claims с reasons, coverage_reason, список missing_information и answers_question последним. Список содержит именно запрошенные факты, на которые ответ не отвечает. answers_question=true допустимо только при пустом списке. Несогласованность отклоняется; приложение никогда автоматически не повышает отрицательный вердикт до положительного.
4. **Контекст проверки.** Verifier получает только полные чанки, на которые ссылаются утверждения. Окружающий текст помогает выявлять условия и противоречия; факты ответа должны подтверждаться выбранными цитатами. Полный retrieval остаётся в выходном JSON для аудита.

Порог, retrieval-профиль, модели и индекс прежние. Номер урока по-прежнему не означает дату реального запуска. Цикл ограничен двумя draft-попытками, без дополнительных verifier-вызовов.

## Применение

Архив содержит актуальную папку `day-24-citations-grounding/` со всеми предыдущими исправлениями. Распакуйте в корень существующего проекта с заменой файлов этой папки. Корневые README, .env, .venv и knowledge.db в архив не входят; пересборка индекса не требуется.

```bash
python day-24-citations-grounding/test_day24.py -v
```

Ожидается 36 тестов и OK. Повторите smoke-проверку:

```bash
python day-24-citations-grounding/main.py ask \
  "Which process periodically collects GitHub repository snapshots into SQLite on Day 18?" \
  --output day-24-citations-grounding/reports/check/worker_audited.json
```

Убедитесь, что retrieval.grounding_protocol равен `quote-ids-coverage-v2`: это показывает, что загружен новый код.

Ожидаемый смысл: независимый worker.py опрашивает наступившие задания и сохраняет GitHub-снимки в SQLite. Нужны цитаты об independent worker и строка, подтверждающая имя файла и сбор данных. Точный набор ID может отличаться после пересборки индекса или изменения порядка найденных чанков.

Принятый ответ: status=answered, непустые sources/quotes, три validation-флага=true. В verdict нужны все supported=true, missing_information=[], answers_question=true и содержательное coverage_reason. Даже такой результат сверяется вручную с цитатами.

После успешной smoke-проверки:

```bash
python day-24-citations-grounding/main.py evaluate \
  --output day-24-citations-grounding/reports/check/evaluate.json
```

Для завершения задания нужны 10 подтверждённых ответов, 2 корректных отказа и ручная проверка каждого ответа через manual_review. Один smoke-ответ не завершает проверку всех вопросов.
