## Образец ответа на вопрос 01

> Каждая тема получает отдельный UUID. Сообщения хранятся в SQLite и привязаны к conversation_id; в запрос к модели попадает история только выбранного диалога. После перезапуска CLI показывает сохранённые диалоги, пользователь выбирает нужный, и его сообщения загружаются из SQLite.

Источники: `day-07-context-persistence/README.md`, разделы Result и How It Works. В данном retrieval source/section/chunk_id: `day-07-context-persistence/README.md` / `README.md` / `3ed667af5d9b09b484ff`.

Прямые цитаты:

> Every new topic receives a UUID. The same `BublikAgent` class can therefore be reused for any dialogue, while each LLM request receives messages only from the selected `conversation_id`.

> The agent now keeps several independent topics between process runs. At startup, the CLI displays previous dialogues, lets the user select one or create another, and reports how many messages were restored for the selected topic.

Критерий принятия: ответ объясняет и разделение контекста по идентификатору, и загрузку сохранённого выбранного диалога. FSM задачи не приписывается переключению диалогов. Факты каждого claim проверяются по его собственным цитатам.

## Образец ответа на вопрос 10

> На VPS сервис bublik-day18 запускает worker.py. Проверьте `sudo systemctl status bublik-day18` и смотрите журнал `journalctl -u bublik-day18 -f`. Через отдельно запускаемый main.py или MCP создайте расписание и запросите свежую сводку; оба процесса должны использовать одну базу BUBLIK_DB_PATH. Для проверки периодичности дождитесь следующего интервала и убедитесь, что появились новый запуск и обновлённая сводка. Наличие active у сервиса само по себе не доказывает успешный сбор.

Последняя часть — проверочная процедура, выведенная из документированных периодического выполнения, записи результатов в журнал и получения свежей сводки, а не сообщение об уже проведённом тесте VPS.

Источники: `day-18-scheduled-mcp/README.md`, Run/VPS; `day-18-scheduled-mcp/README.ru.md`, VPS (systemd) и Проверка пунктов задания; `day-18-scheduled-mcp/bublik-day18.service.example`. В присланном retrieval README.md имеет chunk_id `0e0d09735ed76bf66c2e`, section `README.md`. Unit приведён для проверки аудитором и не выдаётся за найденный моделью чанк.

Прямые цитаты:

```bash

journalctl -u bublik-day18 -f

README на английском допустим как источник: expected_source_hit=false не означает неверный ответ, если найден равнозначный источник.

## Что исправлять и как повторять проверку

1. Проверять область действия каждого утверждения: какая сущность совершает действие и над каким объектом. Совпадение SQLite, restart или названия Bublik не доказывает перенос свойств задач на диалоги.
2. Проверять составные утверждения отдельно: из доказанного запуска worker не следует запуск worker и агента одним сервисом. Вердикт должен отклонять неподтверждённую часть, даже когда другая часть верна.
3. Снова выполнить вопросы 01 и 10 после изменения генерации/проверки. Нужны дословные цитаты и ручная сверка собственных цитат каждого claim. Не заменять проверку смысла поиском ключевых слов.
4. После исправлений выполнить единый полный прогон исходных 10 положительных вопросов и 2 отрицательных контролей. В этом файле нет отрицательных вопросов; режим «не знаю» текущий повторный прогон не проверяет.
5. Для каждого положительного ответа отметить: answer, source + section/chunk_id, quote, дословность, соответствие всей формулировки цитатам и полноту ответа. Для отрицательных: unknown, просьба уточнить, отсутствие выдуманных доказательств. При отсутствии чанков выше порога model_calls должен быть пустым.
